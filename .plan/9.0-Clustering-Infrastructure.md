## 9.1 Executive Summary

This document defines the clustering infrastructure for the FreeBSD native container orchestration system. A cluster is a group of FreeBSD hosts that work together to run container workloads with automatic failover, load distribution, and shared state.

**Key Principles:**
- **No single point of failure** — control plane is distributed, not centralized
- **Gossip beats heartbeats** — scalable membership detection without a coordinator
- **Local state is authoritative** — each node knows its own pods; consensus only for cluster-level decisions
- **Network is transparent** — pods communicate across hosts as if on the same LAN
- **Images propagate automatically** — no manual registry configuration on every node

## 9.2 Cluster Architecture

### 9.2.1 Node Types

| Role | Responsibility | Count |
|------|---------------|-------|
| **Manager** | Stores cluster state, schedules pods, handles API requests | 3-5 (odd number for quorum) |
| **Worker** | Runs pods, reports resource usage, executes health checks | 1-N (scalable) |
| **Storage** | Dedicated ZFS pool for shared volumes (optional) | 0-N |

A manager also runs pods. There is no dedicated "control plane node" that does nothing but manage. Every node contributes compute capacity.

## 9.3 Cluster Formation and Membership

### 9.3.1 Bootstrap Process

```bash
# Initialize the first manager
ocifbsd cluster init --advertise-addr 192.168.1.10 --cluster-name production

# Join additional managers
ocifbsd cluster join --token <token> --manager 192.168.1.10 --advertise-addr 192.168.1.11
ocifbsd cluster join --token <token> --manager 192.168.1.10 --advertise-addr 192.168.1.12

# Join workers
ocifbsd cluster join --token <token> --manager 192.168.1.10 --advertise-addr 192.168.1.20
```

The bootstrap token is a short-lived secret (24h default) that authenticates new nodes. Long-term node identity uses TLS certificates issued by the cluster CA.

### 9.3.2 Gossip-Based Membership

Cluster membership uses a gossip protocol (SWIM-based) rather than a centralized registry:

- Each node maintains a local membership list
- Nodes periodically exchange membership updates with random peers
- New nodes are propagated through the cluster in O(log N) rounds
- Failed nodes are detected through indirect probing

**Why gossip:**
- No single coordinator to fail
- Scales to hundreds of nodes without bottleneck
- Tolerates network partitions gracefully
- Self-healing — nodes rejoin automatically after network recovery

### 9.3.3 Failure Detection

| Detection Method | Trigger | Action |
|-----------------|---------|--------|
| Direct heartbeat timeout | No response for 3 intervals | Mark suspect |
| Indirect probe | K random peers confirm unreachability | Mark failed |
| TCP connection reset | Connection dropped unexpectedly | Immediate suspect |
| Resource heartbeat | Node reports itself unhealthy | Mark degraded |

A node marked **suspect** continues running pods but receives no new placements. A node marked **failed** has its pods rescheduled elsewhere.

## 9.4 Distributed State Storage

### 9.4.1 State Categories

| Category | Examples | Consistency | Storage |
|----------|----------|-------------|---------|
| **Cluster config** | Nodes, tokens, TLS certs | Strong | Raft (managers) |
| **Pod placement** | Which pod runs on which node | Strong | Raft (managers) |
| **Service definitions** | Stack configs, network configs | Strong | Raft (managers) |
| **Runtime state** | Pod status, resource usage | Eventual | Local + gossip |
| **Metrics** | CPU, memory, request rates | Eventual | Time-series DB |

### 9.4.2 Raft Consensus for Critical State

Managers run a Raft consensus group for cluster-level state:

- **Leader election:** Automatic, completes in < 1s on manager failure
- **Log replication:** All state changes replicated to majority before commit
- **Snapshotting:** Periodic snapshots to prevent unbounded log growth
- **Membership changes:** Safe addition/removal of managers via joint consensus

**Why Raft:**
- Well-understood, formally verified algorithms
- FreeBSD has no etcd dependency — we embed our own implementation
- Tuned for small cluster sizes (3-5 managers) typical in on-prem deployments

### 9.4.3 Eventual Consistency for Runtime State

Runtime state (pod health, resource metrics) does not require strong consistency:

- Each node publishes its local state via gossip
- Subscribers update their local view
- Conflicts resolve by timestamp (vector clocks for partition tolerance)
- Stale data is acceptable for metrics; placement decisions use freshest available

## 9.5 Cluster Networking

### 9.5.1 Overlay Network (VXLAN)

All pods across the cluster share a single flat network via VXLAN:

```
Pod A (10.0.1.5) on Worker 1 ──► VXLAN tunnel ──► Pod B (10.0.2.3) on Worker 2
```

**Implementation:**
- Each node creates a `vxlan0` interface
- VXLAN VNI = namespace ID (isolated per namespace)
- Bridge per namespace connects pod VNET interfaces to VXLAN
- No external SDN controller required — configuration distributed via gossip

**Performance:**
- VXLAN adds ~50 bytes per packet (minimal overhead)
- Hardware checksum offload supported on modern NICs
- Direct routing mode for same-subnet nodes (bypass VXLAN when possible)

### 9.5.2 Load Balancing and Service Mesh

Internal service-to-service communication uses cluster-aware load balancing:

```yaml
service:
  name: api
  ports:
    - target: 8080
      publish: 8080
  lb_mode: round_robin   # round_robin, least_conn, ip_hash, random
  health_aware: true     # Skip unhealthy backends automatically
```

**Load Balancer Types:**

| Mode | Algorithm | Use Case |
|------|-----------|----------|
| `round_robin` | Sequential distribution | General purpose |
| `least_conn` | Fewest active connections | Long-lived connections |
| `ip_hash` | Source IP modulo | Session affinity |
| `random` | Uniform random | Large backend pools |
| `weighted` | Manual weight per backend | Heterogeneous hardware |

**Service Mesh Features:**
- Automatic mTLS between pods (via MAC/veriexec)
- Circuit breaking — fail fast when backends are unhealthy
- Retry with exponential backoff
- Request tracing (DTrace-based, zero overhead when not sampling)

### 9.5.3 External Traffic Ingress

External traffic enters the cluster through any node:

```
Internet ──► Node 1 (MetalLB equivalent) ──► VXLAN ──► Pod
         ──► Node 2 (MetalLB equivalent) ──► VXLAN ──► Pod
         ──► Node 3 (MetalLB equivalent) ──► VXLAN ──► Pod
```

**Modes:**

| Mode | Protocol | Requirement |
|------|----------|-------------|
| **ARP/NDP** | Layer 2 | Nodes on same broadcast domain |
| **BGP** | Layer 3 | Router supports BGP peering |
| **DNS round-robin** | DNS | Multiple A/AAAA records |

**ARP/NDP Mode:**
- One node elects itself leader per service IP
- Leader responds to ARP/NDP requests for the service IP
- If leader fails, new leader elected in < 3s
- No router configuration required

**BGP Mode:**
- Each node peers with upstream router
- Announces service IPs with equal cost multipath (ECMP)
- Router distributes traffic across all healthy nodes
- Automatic withdrawal on node failure

## 9.6 Service Discovery

### 9.6.1 DNS-Based Discovery

Every service gets a DNS name resolvable within the cluster:

```
<service>.<stack>.<namespace>.cluster.local
```

Examples:
- `api.myapp.production.cluster.local` → all pods in `api` service
- `db.myapp.production.cluster.local` → all pods in `db` service
- `cache.myapp.production.cluster.local` → all pods in `cache` service

**DNS Implementation:**
- Embedded DNS server on each manager (`ocifbsd-dnsd`)
- Listens on cluster IP (10.0.0.53)
- Forwards unknown queries to upstream resolvers
- Updates records in real-time as pods start/stop

### 9.6.2 API-Based Discovery

Applications can query the cluster API for service endpoints:

```bash
# List endpoints for a service
curl http://cluster.local/v1/services/api.myapp.production/endpoints

# Response:
{
  "service": "api.myapp.production",
  "endpoints": [
    {"ip": "10.0.1.5", "port": 8080, "healthy": true},
    {"ip": "10.0.1.7", "port": 8080, "healthy": true},
    {"ip": "10.0.1.9", "port": 8080, "healthy": false}
  ]
}
```

## 9.7 Image Distribution

### 9.7.1 Layer Caching and Deduplication

Images are stored as ZFS datasets with automatic deduplication:

```
zroot/ocifbsd/images/sha256:abc123...  (base layer)
zroot/ocifbsd/images/sha256:def456...  (app layer)
zroot/ocifbsd/images/sha256:ghi789...  (config layer)
```

**Layer Sharing:**
- Identical layers across images stored once via ZFS dedup
- Clone for each pod — instant, zero-copy
- Snapshot before modification — rollback on failure

### 9.7.2 P2P Image Transfer

When a node needs an image it does not have:

1. Query cluster for nodes that have the image
2. Select closest node (same rack > same datacenter > remote)
3. Stream layers via ZFS send/recv
4. Verify checksums on receipt
5. Cache locally for future use

**No Central Registry Required:**
- Images can be pulled from any node that has them
- New nodes bootstrap from existing nodes
- External registry (Docker Hub, etc.) only needed for initial import
- Air-gapped deployments work out of the box

## 9.8 Failover and High Availability

### 9.8.1 Pod Failover

When a node fails, its pods are rescheduled automatically:

```
1. Node marked failed (failure detection)
2. Leader identifies pods on failed node
3. For each pod:
   a. Check if replicas exist on other nodes (stateless)
   b. If stateful, initiate live migration (if enabled)
   c. If no migration, start new replica from image
4. Update service endpoints
5. Notify load balancers
```

**Stateless pods:** New replica started in < 5s
**Stateful pods with live migration:** < 1s downtime
**Stateful pods without migration:** Depends on image size + startup time

### 9.8.2 Control Plane Failover

Manager nodes run Raft consensus. Failure handling:

| Scenario | Behavior |
|----------|----------|
| 1 manager fails (3 total) | Cluster continues, 2 managers form quorum |
| 2 managers fail (3 total) | Cluster read-only, no new placements |
| Leader fails | New leader elected in < 1s |
| Network partition (managers split) | Minority partition becomes read-only |

**Recovery:**
- Failed managers rejoin automatically when network recovers
- State catches up via Raft log replication
- No manual intervention required for transient failures

### 9.8.3 Network Failover

**VXLAN tunnel failure:**
- Detected via heartbeat over tunnel
- Traffic rerouted through alternate paths (if multi-homed)
- Otherwise, pods on unreachable segment marked failed

**Ingress failure:**
- ARP/NDP leader election fails over in < 3s
- BGP withdraws routes from failed node
- DNS TTLs expire, clients retry next IP

## 9.9 Cluster CLI

```bash
# Initialize a new cluster
ocifbsd cluster init --advertise-addr 192.168.1.10 --cluster-name production

# Join a node to the cluster
ocifbsd cluster join --token <token> --manager 192.168.1.10

# List cluster nodes
ocifbsd node ls

# Inspect a node
ocifbsd node inspect worker-1

# Drain a node (move pods elsewhere)
ocifbsd node drain worker-1

# Remove a node from the cluster
ocifbsd node rm worker-1

# Show cluster status
ocifbsd cluster status

# Rotate cluster CA certificate
ocifbsd cluster rotate-ca

# Backup cluster state
ocifbsd cluster backup > cluster-state.backup

# Restore cluster state
ocifbsd cluster restore < cluster-state.backup
```
