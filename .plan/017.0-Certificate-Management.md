**Branch:** `oci-plan`

## 17.1 Executive Summary

This document defines the comprehensive certificate management system for the FreeBSD native container orchestration cluster. While documents [10.0](./010.0-Security-Credentials-WebUI.md) and [11.0](./011.0-Node-Authentication.md) cover certificate hierarchy and basic rotation, this document focuses on the operational aspects: preserving certificate history, backing up certificates, easily updating every node in the cluster, and recovering nodes that get out of sync.

**Key Principles:**
- **History is immutable** — every certificate ever issued is preserved in a versioned history
- **Backup is automatic** — certificates are backed up via ZFS snapshots and can be exported
- **Updates are coordinated** — certificate changes roll out across the cluster without downtime
- **Recovery is self-service** — an out-of-sync node can recover without manual admin intervention
- **No single point of failure** — certificate state is replicated across managers

**What This Document Covers:**
| Area | Problem | Our Approach |
|------|---------|------------|
| Certificate history | Lost track of old certificates after rotation | ZFS snapshot versioning with automatic retention |
| Backup | No way to restore certificates after disaster | Automatic ZFS snapshots + encrypted export/import |
| Node updates | Updating 100+ nodes manually is error-prone | Coordinated rolling update with automatic verification |
| Out-of-sync recovery | Node misses rotation, can't authenticate | Self-service recovery via bootstrap token re-enrollment |
| CA rotation | Rotating the CA breaks all existing certs | Cross-signed CA transition with overlapping trust period |

## 17.2 Certificate Inventory

### 17.2.1 Cluster CA Certificate

The root of trust for the entire cluster:

| Property | Value |
|----------|-------|
| Location | `/var/lib/ocifbsd/certs/ca.crt` (public), `/var/lib/ocifbsd/certs/ca.key` (private) |
| Storage | ZFS encrypted dataset `zroot/ocifbsd/ca/private` |
| Lifetime | 10 years |
| Key type | Ed25519 (preferred) or RSA-4096 |
| Usage | Signs all node, API, and service account certificates |

**Where it is used:**
- Every node validates peer certificates against this CA
- Every mTLS connection requires the CA cert in the trust chain
- Service account certs are signed by this CA
- API server presents a cert signed by this CA

### 17.2.2 Node Certificates

Every node (manager and worker) has a unique certificate:

| Property | Manager | Worker |
|----------|---------|--------|
| Location | `/var/lib/ocifbsd/certs/node.crt` | `/var/lib/ocifbsd/certs/node.crt` |
| Key location | `/var/lib/ocifbsd/certs/node.key` | `/var/lib/ocifbsd/certs/node.key` |
| Lifetime | 90 days | 90 days |
| Key usage | Server + client auth | Client auth only |
| OU field | `manager` | `worker` |

**Where they are used:**
- Node-to-node mTLS (gossip, image transfer, metrics)
- Node-to-API server authentication
- Raft consensus between managers
- Pod-to-pod mTLS (optional, service mesh)

### 17.2.3 API Server Certificate

The API server certificate is shared across all managers (via Raft-synced state):

| Property | Value |
|----------|-------|
| Location | `/var/lib/ocifbsd/certs/api.crt` |
| Key location | `/var/lib/ocifbsd/certs/api.key` |
| Lifetime | 90 days |
| SAN | `api.<cluster>.svc.cluster.local`, all manager IPs |
| Usage | Server auth only |

**Where it is used:**
- All client connections to the API (CLI, web UI, external tools)
- Node agent connections to managers
- Internal service discovery

### 17.2.4 Service Account Certificates

Per-namespace service account certificates for pod-to-API authentication:

| Property | Value |
|----------|-------|
| Location | `/var/lib/ocifbsd/certs/serviceaccounts/<namespace>/<sa-name>.crt` |
| Key location | `/var/lib/ocifbsd/certs/serviceaccounts/<namespace>/<sa-name>.key` |
| Lifetime | 90 days |
| Usage | Client auth |

**Where they are used:**
- Pods authenticate to the cluster API using these certs
- Service-to-service mTLS within the cluster
- Web UI pod authentication to the API proxy

### 17.2.5 Registry and External Certificates

Certificates for external services:

| Property | Value |
|----------|-------|
| Location | `/var/lib/ocifbsd/certs/external/<name>.crt` |
| Usage | Registry TLS verification, external webhook endpoints, LDAPS |

## 17.3 Certificate Storage and Layout

### 17.3.1 Filesystem Layout

```
/var/lib/ocifbsd/certs/
├── ca.crt                 # Cluster CA public certificate
├── ca.key                 # Cluster CA private key (encrypted)
├── node.crt               # This node's certificate
├── node.key               # This node's private key
├── api.crt                # API server certificate (managers only)
├── api.key                # API server private key (managers only)
├── serviceaccounts/       # Per-namespace service account certs
│   ├── default/
│   │   ├── default.crt
│   │   └── default.key
│   └── webui/
│       ├── webui.crt
│       └── webui.key
├── external/              # External service certs
│   ├── registry.cloudbsd.org.crt
│   └── ldap.company.com.crt
└── history/               # Certificate history (snapshots)
    ├── 2026-04-01T00:00:00Z/
    │   ├── node.crt
    │   └── node.key
    ├── 2026-04-15T00:00:00Z/
    │   ├── node.crt
    │   └── node.key
    └── ...
```

### 17.3.2 ZFS Dataset Structure

Certificates are stored on ZFS for snapshot and encryption benefits:

```
zroot/ocifbsd/certs
├── ca
│   ├── private            # CA private key (AES-256-GCM encrypted)
│   └── public             # CA certificate
├── nodes
│   ├── manager-1          # Per-node cert datasets
│   ├── manager-2
│   ├── worker-1
│   └── worker-2
├── api                    # API server cert (managers only)
├── serviceaccounts        # Service account certs
│   ├── default
│   └── webui
└── external               # External certs
```

**ZFS Properties:**
```bash
zfs set encryption=aes-256-gcm zroot/ocifbsd/certs
zfs set keylocation=prompt zroot/ocifbsd/certs
zfs set compression=zstd zroot/ocifbsd/certs
zfs set snapdir=visible zroot/ocifbsd/certs
```

### 17.3.3 Permissions and Access Control

| File/Directory | Owner | Group | Mode | Access |
|----------------|-------|-------|------|--------|
| `ca.key` | root | ocifbsd-ca | 0400 | `ocifbsdd` (via capability) |
| `ca.crt` | root | wheel | 0444 | All users (public) |
| `node.key` | root | ocifbsd-node | 0400 | `ocifbsdd` only |
| `node.crt` | root | wheel | 0444 | All users |
| `api.key` | root | ocifbsd-api | 0400 | `ocifbsdd` (managers) |
| Service account keys | root | ocifbsd-sa | 0400 | `ocifbsdd` |

## 17.4 Certificate History and Backup

### 17.4.1 Automatic Snapshot History

Every certificate rotation automatically creates a ZFS snapshot:

```bash
# Automatic snapshot on rotation
zfs snapshot zroot/ocifbsd/certs/nodes/manager-1@rotate-2026-04-29-143201
```

**Retention Policy:**
| Age | Retention | Rationale |
|-----|-----------|-----------|
| < 30 days | All snapshots | Full history for debugging |
| 30-90 days | Weekly snapshots | Reduced granularity |
| 90-365 days | Monthly snapshots | Long-term audit trail |
| > 365 days | 4 quarterly snapshots | Compliance minimum |

**Snapshot Naming:**
- Rotation: `rotate-<ISO8601>`
- Manual backup: `backup-<ISO8601>-<reason>`
- Pre-CA-rotation: `pre-ca-rotate-<ISO8601>`

### 17.4.2 Backup Strategies

**Strategy 1: ZFS Send/Receive (Automatic)**
```bash
# Automatic backup to another manager
zfs send zroot/ocifbsd/certs/nodes/manager-1@rotate-2026-04-29-143201 | \
  ssh manager-2 zfs receive zroot/ocifbsd/backups/certs/manager-1
```

**Strategy 2: Encrypted Export (Manual)**
```bash
# Export all certificates for disaster recovery
ocifbsd cert backup export --output /backup/ocifbsd-certs-2026-04-29.tar.gz.enc
# Encrypts with AES-256-GCM + passphrase
```

**Strategy 3: Offline Backup (Admin)**
```bash
# GPG-encrypted export to removable media
ocifbsd cert backup export --gpg-key admin@company.com --output /mnt/usb/certs-backup.tar.gz.gpg
```

**Backup Contents:**
- All current certificates and keys
- All historical snapshots (configurable)
- CA certificate and encrypted private key
- CRL and revocation history
- Certificate metadata (issue dates, serial numbers, node mappings)

### 17.4.3 Export and Import

**Export:**
```bash
# Export current state
ocifbsd cert backup export --output /backup/certs-$(date +%Y%m%d).tar.gz.enc

# Export with specific snapshots
ocifbsd cert backup export --include-snapshots 30d --output /backup/certs-recent.tar.gz.enc
```

**Import:**
```bash
# Import on a new manager
ocifbsd cert backup import /backup/certs-20260429.tar.gz.enc
# Prompts for decryption passphrase
# Verifies CA certificate integrity
# Restores all node certificates
```

## 17.5 Certificate Rotation

### 17.5.1 Rotation Triggers

| Trigger | Action | Lead Time |
|---------|--------|-----------|
| Automatic (80% lifetime) | Initiate rotation | 18 days before expiry |
| Manual admin request | Rotate immediately | Immediate |
| Compromise detected | Emergency rotation | Immediate |
| CA rotation | Full cluster re-issue | Coordinated |

### 17.5.2 Coordinated Rotation Process

The cluster uses a coordinated rotation to ensure no node loses connectivity:

```
Manager detects: cert for worker-3 expires in 72h
    │
    ▼
Generate new certificate for worker-3
    │
    ▼
Store new cert in Raft state (quorum write)
    │
    ▼
Notify worker-3 via authenticated channel
    │
    ▼
worker-3 downloads new cert + key
    │
    ▼
worker-3 atomically replaces cert files
    │
    ▼
worker-3 restarts mTLS listener (dual-cert mode)
    │
    ▼
worker-3 confirms: new connections succeed
    │
    ▼
Manager marks rotation complete
    │
    ▼
Old cert remains valid until expiry (grace period)
```

**Dual-Cert Mode:**
During rotation, nodes accept both old and new certificates:
```c
// Pseudocode for dual-cert acceptance
bool verify_peer_certificate(cert) {
    if (validate_against_current_ca(cert)) return true;
    if (validate_against_previous_ca(cert)) return true;  // During CA rotation
    return false;
}
```

### 17.5.3 Rolling Update Strategy

For cluster-wide rotations (e.g., CA rotation), the cluster uses a rolling update:

```
Phase 1: Managers
  manager-1: rotate → verify → mark healthy
  manager-2: rotate → verify → mark healthy
  manager-3: rotate → verify → mark healthy

Phase 2: Workers (batch of 10% at a time)
  batch-1 (workers 1-10): rotate → verify → mark healthy
  batch-2 (workers 11-20): rotate → verify → mark healthy
  ...

Phase 3: Service accounts (per-namespace)
  namespace-1: rotate all service accounts
  namespace-2: rotate all service accounts
  ...
```

**Safety Checks:**
- If > 5% of nodes in a batch fail rotation, pause and alert
- If a node doesn't confirm within 5 minutes, retry with exponential backoff
- If a node fails 3 retries, mark for manual intervention

### 17.5.4 Rotation Verification

After rotation, the cluster verifies:

```bash
# Automatic verification
ocifbsd cert verify --node worker-3
# Output:
# Certificate: VALID
# Chain: worker-3 → Cluster CA ✓
# Expiry: 2026-07-28 02:39 UTC
# mTLS test: SUCCESS (connected to manager-1, manager-2)
# Gossip test: SUCCESS (5 peers reachable)
```

## 17.6 Node Certificate Update

### 17.6.1 Automatic Update Flow

Nodes automatically update their certificates without admin intervention:

```
Node daemon (ocifbsdd) wakes up (every 1h)
    │
    ▼
Check: cert expires in < 72h?
    │
    ▼ YES
Download new cert from manager (using current valid cert)
    │
    ▼
Validate new cert: signed by CA? correct identity? future expiry?
    │
    ▼
Atomically write new cert to /var/lib/ocifbsd/certs/node.crt.new
    │
    ▼
Rename: node.crt.new → node.crt (atomic)
    │
    ▼
Signal mTLS listener: reload certificates
    │
    ▼
New connections use new cert; old connections drain naturally
    │
    ▼
Report success to manager
    │
    ▼
Manager updates state: "worker-3 rotation complete"
```

### 17.6.2 Manual Update Flow

Admins can force a rotation if needed:

```bash
# Rotate a specific node's certificate
ocifbsd cert rotate --node worker-3

# Rotate all worker certificates
ocifbsd cert rotate --role worker

# Rotate all certificates (emergency)
ocifbsd cert rotate --all --reason "scheduled maintenance"
```

### 17.6.3 Update Verification

After update, the node verifies connectivity:

```bash
# Node self-test after rotation
ocifbsd cert verify --local
# Tests:
# - Can I connect to all managers?
# - Can I authenticate with my new cert?
# - Can I still connect to peers?
# - Is my CRL up to date?
```

## 17.7 Out-of-Sync Node Recovery

### 17.7.1 Detecting Out-of-Sync Nodes

A node is out of sync when:
- Its certificate is expired or revoked
- Its CA certificate doesn't match the cluster's current CA
- It missed a CA rotation and still trusts the old CA
- Its certificate was never rotated (missed automatic update)

**Detection Methods:**
| Method | Frequency | Responsible |
|--------|-----------|-------------|
| Heartbeat cert expiry check | Every 30s | Manager |
| mTLS handshake failure | Every connection | Peer node |
| Admin `ocifbsd cert status` | On-demand | Admin |
| Prometheus metric `cert_days_until_expiry` | Every 1m | Monitoring |

### 17.7.2 Recovery Process

An out-of-sync node recovers automatically without admin intervention:

```
Node detects: certificate expired or CA mismatch
    │
    ▼
Node enters RECOVERY state
    │
    ▼
Node reads bootstrap token from /var/lib/ocifbsd/recovery-token
    │
    ▼
Node connects to manager: "I am worker-3, my cert is expired"
    │
    ▼
Manager validates: Is this node known? Is token valid?
    │
    ▼
Manager issues new certificate (same identity, new serial)
    │
    ▼
Node downloads new cert + CA cert
    │
    ▼
Node atomically replaces certs
    │
    ▼
Node restarts mTLS listener
    │
    ▼
Node verifies: can connect to managers? can gossip?
    │
    ▼
Node returns to HEALTHY state
```

**Recovery Token:**
The recovery token is a long-lived, revocable credential stored securely:
```bash
# Generate recovery token on join
ocifbsd cluster join --token <bootstrap> --manager <ip>
# Creates: /var/lib/ocifbsd/recovery-token
# Permissions: 0400, owned by ocifbsdd
# Content: SWMTKN-RECOVERY-<hash>-<secret>
```

**Security Properties:**
- Recovery token is one-time-use per recovery
- After successful recovery, old token is invalidated, new token issued
- Recovery token can be revoked by admin: `ocifbsd token revoke --recovery worker-3`
- Recovery connections are logged and audited

### 17.7.3 Certificate Reconciliation

If a node has certificates that don't match the cluster state:

```bash
# Admin-triggered reconciliation
ocifbsd cert reconcile --node worker-3

# What happens:
# 1. Manager sends current certificate state for worker-3
# 2. Node compares: local certs vs expected certs
# 3. Node downloads missing or incorrect certs
# 4. Node removes certs that shouldn't exist
# 5. Node verifies all certs are valid
```

## 17.8 CA Rotation and Compromise Recovery

### 17.8.1 Planned CA Rotation

For scheduled CA rotation (e.g., approaching 10-year expiry):

```
Admin initiates: ocifbsd ca rotate --planned
    │
    ▼
Cluster enters CA-ROTATION mode (no new joins allowed)
    │
    ▼
Generate new CA key pair (new passphrase)
    │
    ▼
New CA cert cross-signed by old CA (overlapping trust)
    │
    ▼
Distribute new CA cert to all nodes (gossip + Raft)
    │
    ▼
Nodes enter DUAL-CA mode (trust both old and new)
    │
    ▼
Re-issue all node certificates with new CA
    │
    ▼
Rolling rotation across all nodes (see 17.5.3)
    │
    ▼
All nodes confirm: new CA trusted, new certs working
    │
    ▼
Old CA cert moved to distrust list
    │
    ▼
Old CA cert removed after 30-day grace period
    │
    ▼
Cluster exits CA-ROTATION mode
```

**Cross-Signed CA:**
```
Old CA (expiring 2026)          New CA (expires 2036)
     │                                │
     │  cross-signs                   │
     └───────────────────────────────►│
     │                                │
     │  New CA cert signed by Old CA  │
     │  (validates with Old CA trust) │
```

### 17.8.2 Emergency CA Compromise Recovery

If the CA private key is compromised:

```
Admin detects compromise
    │
    ▼
ocifbsd ca rotate --emergency --reason "private key leaked"
    │
    ▼
Immediate cluster lockdown:
  - No new joins
  - No new pod scheduling
  - All nodes enter maintenance mode
    │
    ▼
Generate new CA key pair (offline if possible)
    │
    ▼
New CA cert distributed with OUT-OF-BAND verification
    │
    ▼
Admin provides verification hash on secure channel
    │
    ▼
Nodes verify new CA cert against out-of-band hash
    │
    ▼
Re-issue ALL certificates (batch operation)
    │
    ▼
Rolling rotation with priority: managers → workers → service accounts
    │
    ▼
Old CA cert immediately distrusted (no grace period)
    │
    ▼
Cluster resumes normal operation
```

**Estimated Downtime:** 5-10 minutes for full cluster

### 17.8.3 Cross-Signed CA Transition

During CA rotation, both CAs are trusted:

```c
// Pseudocode for dual-CA trust
trust_store = {
    current_ca: ca_cert_v2,
    previous_ca: ca_cert_v1,  // During rotation only
    distrusted: [ca_compromised]  // Never trust these
};

bool verify_certificate(cert) {
    if (cert.signed_by(trust_store.current_ca)) return true;
    if (cert.signed_by(trust_store.previous_ca)) {
        log("Certificate validated with previous CA (deprecated)");
        return true;
    }
    return false;
}
```

## 17.9 Certificate Monitoring and Alerting

### 17.9.1 Expiry Monitoring

The cluster continuously monitors certificate expiry:

```bash
# Prometheus metrics exported
ocifbsd_cert_expiry_seconds{node="worker-3",type="node"} 604800
ocifbsd_cert_expiry_seconds{node="manager-1",type="api"} 1209600
```

**Alert Thresholds:**
| Time Until Expiry | Severity | Action |
|-------------------|----------|--------|
| < 30 days | INFO | Log rotation scheduled |
| < 14 days | WARNING | Alert admin, auto-rotation triggered |
| < 7 days | CRITICAL | Page admin, retry rotation every hour |
| < 24 hours | EMERGENCY | Page admin, node marked degraded |
| Expired | DISASTER | Node isolated, recovery required |

### 17.9.2 Health Checks

```bash
# Certificate health check
ocifbsd cert health
# Output:
# CA: VALID (expires 2036-04-29)
# Node cert: VALID (expires 2026-07-28, 89 days remaining)
# API cert: VALID (expires 2026-07-28, 89 days remaining)
# Service accounts: 5/5 VALID
# External certs: 2/2 VALID
# CRL: up to date (last sync: 2026-04-29 14:32 UTC)
# Backup: last snapshot 2026-04-29 00:00 UTC
```

### 17.9.3 Alert Rules

```yaml
# /etc/ocifbsd/alerts/certificates.yaml
alerts:
  - name: cert_expiry_warning
    condition: cert_expiry_seconds < 14 * 86400
    severity: warning
    notify: [email, slack]

  - name: cert_expiry_critical
    condition: cert_expiry_seconds < 7 * 86400
    severity: critical
    notify: [email, slack, pager]

  - name: cert_rotation_failed
    condition: rotation_status == "failed"
    severity: critical
    notify: [email, slack, pager]

  - name: ca_expiry_warning
    condition: ca_expiry_seconds < 365 * 86400
    severity: warning
    notify: [email, slack]
```

## 17.11 Configuration

```yaml
# /etc/ocifbsd/certificates.yaml
certificates:
  # Rotation settings
  rotation:
    enabled: true
    auto_rotate: true
    trigger_at_percent: 80        # Rotate at 80% of lifetime
    retry_interval: 1h             # Retry failed rotations every hour
    max_retries: 3                 # After 3 failures, mark for manual
    grace_period: 72h              # Old cert valid for 72h after rotation
    dual_ca_mode: true            # Trust both old and new CA during rotation

  # History and snapshots
  history:
    snapshots:
      enabled: true
      retention:
        daily: 30                   # Keep 30 daily snapshots
        weekly: 12                 # Keep 12 weekly snapshots
        monthly: 12                # Keep 12 monthly snapshots
        quarterly: 4               # Keep 4 quarterly snapshots

  # Backup settings
  backup:
    auto_backup: true
    interval: 24h                 # Daily automatic backup
    destination: manager-2       # Backup to this manager
    encrypt: true
    compression: zstd
    include_history: true         # Include historical snapshots

  # Recovery settings
  recovery:
    auto_recovery: true            # Allow nodes to self-recover
    recovery_token_ttl: 90d      # Recovery token lifetime
    max_recovery_attempts: 5       # After 5 failures, lock node
    recovery_backoff: 1h         # Wait 1h between recovery attempts

  # Monitoring
  monitoring:
    prometheus_export: true
    check_interval: 1h
    alert_thresholds:
      warning: 14d
      critical: 7d
      emergency: 1d
```

## 17.13 ACME Protocol Support

### 17.13.1 Overview

ACME (Automated Certificate Management Environment) enables automatic certificate issuance and renewal via Let's Encrypt and other ACME-compatible certificate authorities. This is essential for external-facing services that need publicly-trusted certificates without manual intervention.

### 17.13.2 Supported ACME Providers

| Provider | URL | Status | Notes |
|----------|-----|--------|-------|
| Let's Encrypt | `https://acme-v02.api.letsencrypt.org/directory` | Primary | Free, 90-day certs |
| Buypass | `https://api.buypass.com/acme/directory` | Supported | Free, 180-day certs |
| ZeroSSL | `https://acme.zerossl.com/directory` | Supported | Free 90-day trials |
| DigiCert | `https://api.digicert.com/acme/directory` | Supported | Enterprise |
| Custom ACME | User-defined | Supported | Any RFC 8555 compliant |

### 17.13.3 ACME Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                      ACME Client                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ Account Mgmt │  │ Challenge    │  │ Certificate  │      │
│  │              │──│ Handler      │──│ Manager      │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘
         │                   │                  │
         ▼                   ▼                  ▼
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│  ACME Provider  │  │  HTTP-01 /      │  │  Certificate    │
│  (Let's Encrypt)│  │  DNS-01 Challenge│  │  Storage        │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

### 17.13.4 Challenge Types

**HTTP-01 Challenge:**
- Files challenge response to `.well-known/acme-challenge/`
- Automatically creates HTTP service on port 80
- Requires port 80 to be accessible from the internet
- Automatic cleanup after validation

**DNS-01 Challenge:**
- Creates TXT record at `_acme-challenge.<domain>`
- Supports multiple DNS providers:
  - Cloudflare
  - Route53 (AWS)
  - Azure DNS
  - Google Cloud DNS
  - Generic RFC 2136 (bind-compatible)
- Requires DNS API credentials

**TLS-ALPN-01 Challenge:**
- Serves challenge over TLS on port 443
- No HTTP server required
- Useful when only HTTPS is exposed

### 17.13.5 ACME CLI Commands

```bash
# Configure ACME provider
ocifbsd acme provider set --provider letsencrypt --email admin@example.com
ocifbsd acme provider set --provider custom --server https://acme.example.com/directory

# Register ACME account
ocifbsd acme account register --accept-terms
ocifbsd acme account update --email new-email@example.com

# Request certificate for domain
ocifbsd acme cert request --domain api.example.com --challenge http-01
ocifbsd acme cert request --domain "*.example.com" --challenge dns-01 --dns-provider cloudflare

# List and manage ACME certificates
ocifbsd acme cert list
ocifbsd acme cert show api.example.com
ocifbsd acme cert renew api.example.com
ocifbsd acme cert revoke api.example.com --reason key-compromise

# DNS provider configuration
ocifbsd acme dns set cloudflare --api-token <token>
ocifbsd acme dns set route53 --access-key <key> --secret-key <secret>
ocifbsd acme dns verify --provider cloudflare
```

### 17.13.6 ACME Configuration

```yaml
# /etc/ocifbsd/acme.yaml
acme:
  # ACME provider settings
  provider:
    type: letsencrypt          # letsencrypt, buypass, zerossl, custom
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    
  # Challenge settings
  challenge:
    type: http-01             # http-01, dns-01, tls-alpn-01
    http_port: 80             # For HTTP-01
    tls_port: 443             # For TLS-ALPN-01
    http_timeout: 30s
    propagation_timeout: 120s # For DNS-01
    
  # DNS provider for DNS-01 challenges
  dns:
    provider: cloudflare
    api_token: ${CLOUDFLARE_API_TOKEN}
    # Or for Route53:
    # provider: route53
    # access_key: ${AWS_ACCESS_KEY}
    # secret_key: ${AWS_SECRET_KEY}
    # region: us-east-1

  certificate:
    key_type: ecdsa           # rsa, ecdsa
    key_size: 2048            # For RSA
    ecdsa_curve: p384         # For ECDSA (p256, p384, p521)

    auto_renew: true

    certificates_per_domain: 50
    duplicate_limit_window: 168h
    failed_validation_limit: 5
    failed_validation_window: 1h
```

## 17.14 External CA Integration

### 17.14.1 Overview

External CA integration allows the cluster to use certificates from corporate or enterprise PKI (Certificate Authorities) instead of or alongside the internal cluster CA. This is essential for:
- Enterprise environments with existing PKI infrastructure
- Compliance requirements for specific CA providers
- Hybrid environments requiring trust with both internal and external systems
- High-security environments requiring hardware-backed CA

### 17.14.2 Supported External CA Types

| CA Type | Examples | Key Features |
|---------|----------|--------------|
| Microsoft AD CS | Windows Server CA | Active Directory integration, certificate templates |
| EJBCA | KeyFactor, PrimeKey | Enterprise PKI, SCEP support |
| Dogtag | Red Hat PKI | FreeIPA integration |
| Vault PKI | HashiCorp Vault | Dynamic certificates, short-lived certs |
| Cloud PKI | AWS ACM Private CA, Azure Key Vault | Cloud-native, HSM-backed |
| Custom | Any RFC 5280 CA | Generic SCEP/EST/CMP support |

### 17.14.3 Integration Methods

**SCEP (Simple Certificate Enrollment Protocol):**
```
┌──────────┐      SCEP Request      ┌──────────┐
│  Node    │ ──────────────────────▶ │  CA      │
│  Agent   │ ◀────────────────────── │  Server  │
└──────────┘      Certificate       └──────────┘
```
- Most widely supported
- Challenge password for authorization
- Manual approval option

**EST (Enrollment over Secure Transport):**
```
┌──────────┐      TLS + HTTP        ┌──────────┐
│  Node    │ ══════════════════════▶│  CA       │
│  Agent   │ ◀══════════════════════ │  Server  │
└──────────┘      Certificate       └──────────┘
```
- Uses TLS client certificates
- More secure than SCEP
- Supports key generation on CA

**CMP (Certificate Management Protocol):**
- Most feature-rich
- Supports key update
- Complex but powerful

### 17.14.4 External CA Configuration

```yaml
# /etc/ocifbsd/external-ca.yaml
external_ca:
  # Microsoft AD CS
  adcs:
    enabled: true
    server: https://pki.company.com/certsrv
    auth_method: ntlm              # ntlm, basic, cert-based
    template: OCI-Node
    enrollment_mode: manual        # manual, auto
    require_approval: true
    approval_wait_time: 5m
    
  # HashiCorp Vault PKI
  vault_pki:
    enabled: false
    server: https://vault.company.com
    auth_method: kubernetes        # kubernetes, token, approle
    role: ocifbsd-nodes
    lease_ttl: 8760h              # 1 year
    max_ttl: 87600h               # 10 years
    renew_before: 720h             # Renew 30 days before expiry
    
  # AWS ACM Private CA
  aws_pca:
    enabled: false
    region: us-east-1
    ca_arn: arn:aws:acm-pca:...
    enrollment_arn: arn:aws:acm-pca:...
    validity: 365d
    key_algorithm: RSA_2048
    
  # SCEP Configuration
  scep:
    enabled: true
    server_url: https://pki.company.com/SCEP/
    challenge_password: ${SCEP_CHALLENGE}
    key_type: RSA
    key_size: 2048
    digest_algorithm: sha256
    
  # Trust settings
  trust:
    import_external_ca: true       # Add external CA to system trust store
    cluster_trust_mode: cross-sign # cross-sign, subordinate, parallel
    allow_mixed_mode: true         # Allow both internal and external certs
```
