# 11. Node Authentication and Inter-Node Trust

**Author:** Mark LaPointe <mark@cloudbsd.org>
**Date:** 2026-04-29
**Repository:** https://github.com/cloudbsdorg/freebsd-src-oci
**Branch:** `oci-plan`

---

## 11.1 Executive Summary

This document defines how every node in the cluster proves its identity to every other node. Authentication is not a one-time event at join time — it is continuous, mutual, and enforced on every connection.

**Key Principles:**
- **Bootstrap once, trust never** — a node proves itself at join time and on every subsequent connection
- **Mutual TLS everywhere** — every node presents a certificate; every node validates the peer's certificate
- **No shared secrets in config files** — bootstrap tokens are short-lived; long-term identity is cryptographic
- **Compromised nodes can be isolated** — revocation is immediate and cluster-wide
- **Certificate rotation is automatic** — no manual intervention, no downtime

**Authentication Flows Covered:**
| Flow | Mechanism | Frequency |
|------|-----------|-----------|
| Node joins cluster | Bootstrap token + CSR | Once per node lifetime |
| Node-to-node gossip | mTLS with pinned CA | Every gossip packet |
| Node-to-API server | mTLS + token | Every API request |
| Pod-to-pod (optional) | mTLS with service account cert | Every connection |
| Control plane Raft | mTLS between managers | Every log entry |

## 11.2 Authentication Architecture

### 11.2.1 Trust Model

The cluster operates on a **single-root trust model** with distributed verification:

```
┌─────────────────────────────────────────┐
│         Cluster CA (Root of Trust)       │
│         ┌─────────────────┐              │
│         │  Private key    │              │
│         │  (HSM or        │              │
│         │   encrypted ZFS)│              │
│         └─────────────────┘              │
│                    │                     │
│    ┌───────────────┼───────────────┐    │
│    ▼               ▼               ▼    │
│ Manager 1      Manager 2      Manager 3 │
│  Cert +        Cert +         Cert +    │
│  Key           Key            Key       │
│    │               │               │    │
│    └───────────────┼───────────────┘    │
│                    │                     │
│         ┌──────────┴──────────┐         │
│         ▼                     ▼         │
│      Worker 1              Worker 2     │
│       Cert +                Cert +      │
│       Key                   Key         │
└─────────────────────────────────────────┘
```

**Properties:**
- The cluster CA is created when the first manager initializes
- The CA private key is stored encrypted (ZFS encryption or HSM)
- Every node receives a unique certificate signed by the CA
- Every node has the CA public certificate to validate peers
- No node can forge another node's identity without the CA private key

### 11.2.2 Certificate Hierarchy

```
Cluster CA (self-signed root)
│
├── Manager Certificates (server + client auth)
│   ├── manager-1.production.cluster.local
│   ├── manager-2.production.cluster.local
│   └── manager-3.production.cluster.local
│
├── Worker Certificates (client auth only)
│   ├── worker-1.production.cluster.local
│   ├── worker-2.production.cluster.local
│   └── worker-3.production.cluster.local
│
├── API Server Certificate (server auth)
│   └── api.production.cluster.local
│
├── Service Account Certificates (per-namespace)
│   ├── default.production.svc.cluster.local
│   └── webui.system.svc.cluster.local
│
└── etcd/Raft Peer Certificates (peer auth)
    ├── raft-1.production.cluster.local
    ├── raft-2.production.cluster.local
    └── raft-3.production.cluster.local
```

**Certificate Fields:**
| Field | Value | Purpose |
|-------|-------|---------|
| `CN` | Node hostname | Human-readable identity |
| `O` | Cluster name | Cluster scope |
| `OU` | Node role (manager/worker) | Role-based validation |
| `SAN` | IP addresses, hostnames | Network-level identity |
| `serialNumber` | UUID | Unique node identifier |

### 11.2.3 Cluster Certificate Authority

The CA is distributed across managers for availability but protected for security:

```
┌─────────────────────────────────────────┐
│         CA Private Key Storage           │
│                                          │
│  ┌─────────────────────────────────┐    │
│  │  Primary: Encrypted ZFS dataset │    │
│  │  zroot/ocifbsd/ca/private       │    │
│  │  (AES-256-GCM, passphrase)      │    │
│  └─────────────────────────────────┘    │
│                                          │
│  ┌─────────────────────────────────┐    │
│  │  Optional: HSM (YubiHSM, NitroKey)│    │
│  │  Key never leaves hardware        │    │
│  └─────────────────────────────────┘    │
│                                          │
│  ┌─────────────────────────────────┐    │
│  │  Backup: GPG-encrypted offline   │    │
│  │  Store in separate location      │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**CA Operations:**
| Operation | Who Can Request | How |
|-----------|----------------|-----|
| Issue certificate | Any node with valid bootstrap token | CSR to any manager |
| Revoke certificate | Manager with quorum | Raft consensus |
| Rotate CA | Manager with quorum + manual confirmation | Multi-step process |
| Backup CA key | Admin only | Offline encrypted export |

## 11.3 Node Bootstrap and Enrollment

### 11.3.1 First Manager Initialization

The first manager creates the cluster and becomes the initial CA:

```bash
# Initialize the first manager
ocifbsd cluster init \
  --advertise-addr 192.168.1.10 \
  --cluster-name production \
  --ca-passphrase-file /root/.ocifbsd/ca-passphrase
```

**What happens:**
1. Generate 4096-bit RSA or Ed25519 CA key pair
2. Create self-signed CA certificate (10-year validity)
3. Encrypt private key with passphrase (ZFS dataset encryption)
4. Generate manager certificate signed by CA
5. Start API server with manager certificate
6. Generate initial bootstrap token (24h validity)
7. Print join command for other nodes

```
Manager 1 Boot
    │
    ▼
Generate CA Key Pair
    │
    ▼
Create CA Certificate (self-signed)
    │
    ▼
Encrypt Private Key ──► ZFS encrypted dataset
    │
    ▼
Generate Manager 1 Certificate
    │
    ▼
Start API Server (TLS on :6443)
    │
    ▼
Generate Bootstrap Token
    │
    ▼
Cluster Ready for Joins
```

### 11.3.2 Manager Join Flow

Additional managers join via authenticated CSR:

```bash
# On the new manager node
ocifbsd cluster join \
  --token SWMTKN-1-xxx \
  --manager 192.168.1.10 \
  --advertise-addr 192.168.1.11 \
  --role manager
```

**Step-by-step:**

```
New Manager                          Existing Manager
    │                                    │
    │  1. Generate local key pair        │
    │─────────────────────────────────────►│
    │                                    │
    │  2. Create CSR with node info      │
    │     (CN, SAN, role=manager)        │
    │                                    │
    │  3. Send CSR + bootstrap token     │
    │─────────────────────────────────────►│
    │                                    │
    │                                    │  4. Validate token
    │                                    │     (check expiry,
    │                                    │      not revoked)
    │                                    │
    │                                    │  5. Verify CSR
    │                                    │     (valid fields,
    │                                    │      role matches)
    │                                    │
    │                                    │  6. Sign CSR with CA
    │                                    │     (manager cert issued)
    │                                    │
    │  7. Return certificate + CA cert   │
    │◄─────────────────────────────────────│
    │                                    │
    │  8. Store certificate and CA cert  │
    │     (encrypted ZFS dataset)         │
    │                                    │
    │  9. Start gossip + API client      │
    │     (mTLS from now on)             │
    │                                    │
    │  10. Join Raft consensus group      │
    │─────────────────────────────────────►│
    │                                    │
    │  11. Sync cluster state             │
    │◄─────────────────────────────────────│
    │                                    │
```

**Security checks during join:**
| Check | Failure Action |
|-------|---------------|
| Token expired or invalid | Reject join, log attempt |
| Token already used (one-time) | Reject join, alert admin |
| CSR role != token role | Reject join, log mismatch |
| CSR SAN doesn't match source IP | Reject join, possible MITM |
| Manager quorum would be even | Warn, but allow (user override) |

### 11.3.3 Worker Join Flow

Workers follow the same flow but receive client-only certificates:

```bash
# On the new worker node
ocifbsd cluster join \
  --token SWMTKN-1-xxx \
  --manager 192.168.1.10 \
  --advertise-addr 192.168.1.20 \
  --role worker
```

**Differences from manager join:**
- Worker certificates have `OU=worker` (not manager)
- Workers do not join Raft consensus
- Workers receive read-only access to cluster state
- Workers cannot issue certificates or approve CSRs

### 11.3.4 Bootstrap Tokens

Bootstrap tokens are short-lived, one-time credentials for initial enrollment:

```
Token Format: SWMTKN-1-<hash>-<secret>

Example: SWMTKN-1-3pu6hsy7jxql9q3i2q3q3q3q-3pu6hsy7jxql9q3i2q3q3q3q
```

**Token Properties:**
| Property | Value | Rationale |
|----------|-------|-----------|
| Lifetime | 24 hours default | Long enough for provisioning, short enough to limit exposure |
| Usage limit | 1 use default | Prevents replay after legitimate use |
| Scope | manager or worker | Token can only issue certs for declared role |
| Revocable | Yes | Admin can revoke before expiry |

**Token Management:**
```bash
# Create a new bootstrap token (manager role, 48h expiry)
ocifbsd token create --role manager --ttl 48h
# Output: SWMTKN-1-xxx

# List active tokens
ocifbsd token ls
# TOKEN ID          ROLE      EXPIRES                 USED
# 3pu6hsy7jxq       manager   2026-04-30 02:39 UTC  no
# 8kx9mzt4bvn       worker    2026-04-29 14:39 UTC  yes

# Revoke a token before expiry
ocifbsd token revoke 3pu6hsy7jxq

# Rotate all tokens (emergency)
ocifbsd token rotate --all
```

## 11.4 Mutual TLS Between Nodes

### 11.4.1 TLS Handshake

Every connection between nodes begins with mutual TLS:

```
Client (Node A)                  Server (Node B)
    │                                │
    │  1. ClientHello                │
    │     (supported ciphers,         │
    │      random nonce)             │
    │───────────────────────────────►│
    │                                │
    │  2. ServerHello + Certificate  │
    │     (server cert, chain,       │
    │      random nonce)             │
    │◄───────────────────────────────│
    │                                │
    │  3. Validate server cert       │
    │     - Signed by cluster CA?     │
    │     - Not expired?              │
    │     - Not revoked?              │
    │     - SAN matches hostname/IP?  │
    │                                │
    │  4. Client Certificate          │
    │     (client cert + chain)      │
    │───────────────────────────────►│
    │                                │
    │  5. Validate client cert        │
    │     (same checks as step 3)    │
    │                                │
    │  6. Key exchange + Finished    │
    │◄───────────────────────────────│
    │                                │
    │  7. Encrypted application data │
    │◄───────────────────────────────│
    │───────────────────────────────►│
```

**TLS Configuration:**
| Parameter | Value |
|-----------|-------|
| Minimum version | TLS 1.3 |
| Cipher suites | TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256 |
| Certificate type | x509v3 |
| Key type | Ed25519 (preferred) or RSA-4096 |
| Mutual auth | Required (verify_client = always) |

### 11.4.2 Certificate Validation

Every certificate presented is validated against multiple criteria:

```c
// Pseudocode for certificate validation
bool validate_peer_certificate(cert, expected_role) {
    // 1. Chain of trust
    if (!cert.verify_signature(ca_public_key)) {
        log_security_event("INVALID_SIGNATURE", cert);
        return false;
    }

    // 2. Expiry
    if (cert.not_after < now() || cert.not_before > now()) {
        log_security_event("CERT_EXPIRED", cert);
        return false;
    }

    // 3. Revocation
    if (crl.contains(cert.serial)) {
        log_security_event("CERT_REVOKED", cert);
        return false;
    }

    // 4. Role validation
    if (cert.ou != expected_role) {
        log_security_event("ROLE_MISMATCH", cert);
        return false;
    }

    // 5. Cluster scope
    if (cert.o != cluster_name) {
        log_security_event("WRONG_CLUSTER", cert);
        return false;
    }

    // 6. Identity binding
    if (!known_nodes.contains(cert.serial)) {
        log_security_event("UNKNOWN_NODE", cert);
        return false;
    }

    return true;
}
```

### 11.4.3 Connection Establishment

After TLS handshake, nodes verify each other at the application layer:

```
Node A ──► Node B

1. TLS handshake (mTLS)
2. Node A sends: "I am node-a, my UUID is xxx"
3. Node B checks: UUID matches certificate serialNumber?
4. Node B sends: "I am node-b, my UUID is yyy"
5. Node A checks: UUID matches certificate serialNumber?
6. Both nodes record: "Authenticated connection to peer"
7. Connection ready for gossip/API/raft traffic
```

**Connection Types and Auth:**
| Connection | Initiator | Authenticator | Purpose |
|------------|-----------|-------------|---------|
| Gossip | Any node | Any node | Membership, health |
| API client | Any node | Manager | State queries, commands |
| Raft peer | Manager | Manager | Consensus log replication |
| Image transfer | Any node | Any node | ZFS send/recv |
| Metrics | Any node | Manager | Resource reporting |

## 11.5 Gossip Protocol Authentication

### 11.5.1 Gossip Message Integrity

Gossip messages are signed to prevent tampering:

```
Gossip Packet Structure:
┌─────────────────────────────────────────┐
│  Header (sender UUID, timestamp, type)   │
├─────────────────────────────────────────┤
│  Payload (membership update, health)    │
├─────────────────────────────────────────┤
│  Signature (Ed25519, sender's key)       │
└─────────────────────────────────────────┘
```

**Validation:**
1. Extract sender UUID from header
2. Look up sender's public key from certificate store
3. Verify signature against header + payload
4. Check timestamp is within 60-second window (prevent replay)
5. Process payload only if all checks pass

### 11.5.2 Gossip Membership Verification

When a node learns about another node via gossip, it verifies before trusting:

```
Node A hears about Node C from Node B

1. Node A already trusts Node B (validated mTLS)
2. Node B says: "Node C is at 192.168.1.22, healthy"
3. Node A does NOT trust this yet
4. Node A initiates direct mTLS connection to Node C
5. Node A validates Node C's certificate independently
6. Only then does Node A add Node C to its membership list
```

**Why indirect gossip is not trusted:**
- Prevents compromised nodes from injecting fake members
- Every node validates every other node directly
- Membership is transitive only through cryptographic proof

## 11.6 API Server Authentication

### 11.6.1 Client to API Server

All API clients authenticate to manager nodes:

```
Client Types:
┌─────────────────────────────────────────┐
│  1. Node (worker/manager)                │
│     Auth: mTLS client certificate        │
│     Scope: node-level operations         │
├─────────────────────────────────────────┤
│  2. User (human, CLI)                    │
│     Auth: Token (JWT) or client cert     │
│     Scope: RBAC-defined                  │
├─────────────────────────────────────────┤
│  3. Service Account (pod)                │
│     Auth: mTLS service account cert      │
│     Scope: namespace-level               │
├─────────────────────────────────────────┤
│  4. Web UI                               │
│     Auth: Token (user login)             │
│     Scope: RBAC-defined                  │
└─────────────────────────────────────────┘
```

**API Request Authentication:**
```bash
# Node making API call (automatic, uses node cert)
curl --cert /var/lib/ocifbsd/certs/node.crt \
     --key /var/lib/ocifbsd/certs/node.key \
     --cacert /var/lib/ocifbsd/certs/ca.crt \
     https://manager-1:6443/v1/pods

# User making API call (token-based)
curl -H "Authorization: Bearer $TOKEN" \
     https://manager-1:6443/v1/pods

# Service account inside pod (automatically mounted)
curl --cert /var/run/ocifbsd/serviceaccount/cert.pem \
     --key /var/run/ocifbsd/serviceaccount/key.pem \
     https://api.production.svc:6443/v1/services
```

### 11.6.2 API Server to Node

When the API server pushes commands to nodes (e.g., start a pod), the node validates the server:

```
Manager API Server ──► Worker Node

1. API server connects to worker node agent (port 10250)
2. Worker presents its certificate (client auth)
3. API server presents its certificate (server auth)
4. Worker validates:
   - API server cert is signed by cluster CA
   - API server cert has OU=manager
   - API server cert is not revoked
5. Only then does worker accept the command
```

**This prevents:**
- Rogue managers sending commands
- Compromised API endpoints controlling nodes
- Man-in-the-middle command injection

## 11.7 Certificate Lifecycle

### 11.7.1 Rotation Schedule

| Certificate Type | Lifetime | Rotation Trigger | Rotation Window |
|-----------------|----------|------------------|-----------------|
| CA certificate | 10 years | Manual only | Admin-initiated |
| Manager node | 90 days | 80% of lifetime | 72 hours before expiry |
| Worker node | 90 days | 80% of lifetime | 72 hours before expiry |
| API server | 90 days | 80% of lifetime | 72 hours before expiry |
| Service account | 90 days | 80% of lifetime | 72 hours before expiry |
| Bootstrap token | 24 hours | N/A (one-time) | N/A |

### 11.7.2 Rotation Process

Automatic rotation requires no downtime:

```
Node detects: cert expires in 72h
    │
    ▼
Generate new key pair locally
    │
    ▼
Create CSR with same identity
    │
    ▼
Send CSR to manager (using current valid cert)
    │
    ▼
Manager validates CSR, signs new cert
    │
    ▼
Node receives new cert
    │
    ▼
Atomically update cert file
    │
    ▼
New connections use new cert
    │
    ▼
Old cert remains valid until expiry
    │
    ▼
After expiry, old cert purged
```

**Rotation Safety:**
- New cert is valid immediately (overlapping validity)
- Old cert continues to work until expiry
- If rotation fails, node retries every hour
- Alert if rotation fails with < 24h remaining

### 11.7.3 Expiry Handling

```
Certificate Expiry Timeline:

T-72h:  Rotation triggered automatically
        ├─ New cert requested
        └─ Alert: "Certificate rotation started"

T-24h:  If rotation failed:
        ├─ CRITICAL alert: "Certificate expires in 24h"
        └─ Retry every 15 minutes

T-1h:   If still not rotated:
        ├─ Node marks itself degraded
        ├─ No new pods scheduled
        └─ Emergency: admin must intervene

T-0:    Certificate expires
        ├─ Node cannot authenticate
        ├─ Node marked failed
        ├─ Pods rescheduled
        └─ Node must re-enroll with bootstrap token
```

## 11.8 Revocation and Lockout

### 11.8.1 Certificate Revocation List

The cluster maintains a distributed CRL:

```
CRL Distribution:
┌─────────────────────────────────────────┐
│         CRL Master (Manager 1)           │
│  ┌─────────────────────────────────┐    │
│  │  CRL: revoked serial numbers     │    │
│  │  + revocation timestamp          │    │
│  │  + reason code                   │    │
│  └─────────────────────────────────┘    │
│              │                           │
│              ▼                           │
│  ┌─────────────────────────────────┐    │
│  │  Replicated via Raft to all      │    │
│  │  managers                        │    │
│  └─────────────────────────────────┘    │
│              │                           │
│              ▼                           │
│  ┌─────────────────────────────────┐    │
│  │  Distributed to all nodes via    │    │
│  │  gossip (periodic sync)          │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**Revocation Reasons:**
| Code | Reason | Action |
|------|--------|--------|
| `compromised` | Private key leaked | Immediate isolation |
| `decommissioned` | Node removed from cluster | Graceful drain then revoke |
| `superseded` | Certificate rotated early | Old cert revoked after overlap |
| `admin_hold` | Administrative suspension | Node paused, no new work |

**CRL CLI:**
```bash
# Revoke a node's certificate
ocifbsd cert revoke worker-2 --reason compromised

# List revoked certificates
ocifbsd cert revoked
# SERIAL              NODE       REVOKED AT              REASON
# 3pu6hsy7jxq         worker-2   2026-04-29 02:39 UTC    compromised

# Check if a certificate is revoked
ocifbsd cert check worker-2
# Status: REVOKED (reason: compromised, at: 2026-04-29 02:39 UTC)
```

### 11.8.2 Emergency Node Lockout

When a node is compromised, lockout is immediate:

```
Admin detects compromise
    │
    ▼
ocifbsd node lockout worker-2 --reason "suspicious activity"
    │
    ▼
1. Certificate added to CRL
2. CRL propagated to all nodes (< 5 seconds)
3. All nodes drop connections to worker-2
4. worker-2 pods marked failed, rescheduled
5. worker-2 isolated at network layer (pf block)
6. Audit log: "Emergency lockout of worker-2"
    │
    ▼
worker-2 cannot rejoin without new bootstrap token
```

### 11.8.3 Compromised CA Recovery

If the CA private key is compromised, the cluster must rotate the entire PKI:

```
CA Compromise Recovery:

1. Admin initiates: ocifbsd ca rotate --emergency
2. Cluster enters maintenance mode (no new joins)
3. Generate new CA key pair (offline if possible)
4. New CA certificate issued
5. Re-issue all node certificates (batch operation)
6. Distribute new CA cert to all nodes
7. Nodes verify new CA cert via out-of-band hash
8. Old CA cert added to distrust list
9. Cluster resumes normal operation

Estimated downtime: 5-10 minutes for full cluster
```

## 11.9 Authentication CLI

```bash
# Initialize cluster CA and first manager
ocifbsd cluster init --advertise-addr <ip> --cluster-name <name>

# Join a node to the cluster
ocifbsd cluster join --token <token> --manager <ip> --advertise-addr <ip>

# Create a bootstrap token
ocifbsd token create --role <manager|worker> [--ttl <hours>]

# List active tokens
ocifbsd token ls

# Revoke a token
ocifbsd token revoke <token-id>

# Rotate all tokens
ocifbsd token rotate --all

# View node certificate
ocifbsd cert show

# Rotate node certificate early
ocifbsd cert rotate

# Revoke a node's certificate
```
