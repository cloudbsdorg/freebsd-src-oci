# 16. Garbage Collection and Orphaned Resource Management

**Author:** Mark LaPointe <mark@cloudbsd.org>

**Repository:** https://github.com/cloudbsdorg/freebsd-src-oci
**Branch:** `oci-plan`

## 16.1 Executive Summary

This document defines the garbage collection (GC) architecture for the FreeBSD native container orchestration system. Garbage collection is not an afterthought — it is a core subsystem that prevents resource leaks, disk exhaustion, and the accumulation of orphaned containers, images, volumes, and network interfaces that plague production Kubernetes clusters.

**Key Principles:**
- **Proactive, not reactive** — GC runs continuously, not just when disk is full
- **Ownership is explicit** — every resource has an owner; when the owner disappears, the resource is collected
- **Graceful degradation** — GC never deletes active resources; it only cleans up what is truly orphaned
- **Observable** — every GC action is logged, auditable, and reversible (within retention window)
- **Cluster-aware** — GC coordinates across nodes to handle distributed orphans

**What This Document Covers:**
| Area | Problem | Our Approach |
|------|---------|------------|
| Orphaned pods | Node crashes, controller bugs, force-deletes leave pods running | Ownership graph + heartbeat-based orphan detection |
| Image bloat | Unused images accumulate, filling ZFS pools | Reference-counted layers + automatic pruning |
| Volume leaks | PVCs left behind after namespace deletion | Owner-reference tracking + cascade delete |
| Network orphans | Bridges, epairs, VXLAN interfaces left after pod death | Interface tagging + lifecycle binding |
| Stuck terminating | Pods hang in `Terminating` forever | Forced cleanup with timeout and audit |
| Failed job accumulation | Completed/failed pods never cleaned up | TTL-based automatic deletion |

## 16.2 What Is an Orphaned Pod

An **orphaned pod** is a jail (or set of jails) that is running on a node but is no longer managed by the orchestrator. The orchestrator has lost track of it, but the processes, network interfaces, and storage remain.

### 16.2.1 How Pods Become Orphaned

| Scenario | Cause | Result |
|----------|-------|--------|
| Node crash | Manager loses connection to worker; worker reboots with running jails | Worker has jails the manager doesn't know about |
| Force delete | Admin runs `jail -r` or `kill -9` on the orchestrator daemon | Daemon loses state; jails keep running |
| Controller bug | Scheduler or controller crashes mid-operation | Pod created but not recorded in state |
| Network partition | Worker isolated from managers for >heartbeat timeout | Manager marks node dead; worker still runs pods |
| Partial delete | `ocifbsd pod delete` fails after removing state but before stopping jail | State gone, jail still running |
| Stack delete | Stack removed but pod cleanup fails silently | Pods remain, stack is gone |

### 16.2.2 The Kubernetes Garbage Collection Problem

Kubernetes has a garbage collector, but it is notoriously problematic:

| Kubernetes Issue | Root Cause | Impact |
|------------------|------------|--------|
| `ownerReferences` not set | Controllers forget to set ownership | Resources leak forever |
| Cascade delete fails | API server overload or etcd timeout | Children outlive parents |
| Finalizers block forever | External controller doesn't remove finalizer | Pod stuck `Terminating` for days |
| Orphaned pods on dead nodes | Node object deleted but kubelet not told | Pods keep running, invisible to cluster |
| Image GC too aggressive | kubelet deletes images in use | Running pods lose filesystem layers |
| Image GC too conservative | kubelet never deletes unused images | Disk fills up |
| PVC protection | PVC has `kubernetes.io/pvc-protection` finalizer | PVC blocks namespace deletion indefinitely |

**Our approach:** Design GC into the system from the start, not as a bolt-on controller. Every resource has mandatory ownership. Orphan detection is local and immediate, not API-server-dependent.

## 16.3 Garbage Collection Architecture

### 16.3.1 Design Principles

1. **Local authority wins** — The node that runs a jail is the authoritative source of whether it exists. The manager's state is a cache, not the truth.
2. **Ownership graph is mandatory** — Every resource (jail, dataset, interface, rule) must have an `owner` field. No owner = immediate GC candidate.
3. **Heartbeat-based liveness** — Managers and workers exchange heartbeats. If a worker misses N heartbeats, the manager initiates orphan detection on that node.
4. **Grace period** — Orphans are not killed immediately. They enter a `pending-deletion` state for a configurable grace period (default: 5 minutes) to allow for transient network issues.
5. **Audit everything** — Every GC action generates an event. Admins can see what was deleted, when, and why.

### 16.3.2 Ownership Graph

```
Stack "web-app"
  └── Pod "web-1" (owner: stack/web-app)
        ├── Jail "web-1-main" (owner: pod/web-1)
        │     ├── ZFS dataset "zroot/ocifbsd/pods/web-1/rootfs" (owner: jail/web-1-main)
        │     ├── epair interface "epair1a" (owner: jail/web-1-main)
        │     ├── RCTL rules (owner: jail/web-1-main)
        │     └── MAC label (owner: jail/web-1-main)
        ├── Volume "web-1-data" (owner: pod/web-1)
        │     └── ZFS dataset "zroot/ocifbsd/volumes/web-1-data" (owner: volume/web-1-data)
        └── Secret "web-1-tls" (owner: pod/web-1)
              └── ZFS dataset "zroot/ocifbsd/secrets/web-1-tls" (owner: secret/web-1-tls)
```

**GC Rule:** If `Stack "web-app"` is deleted, all children are cascade-deleted. If a child cannot be deleted (e.g., volume is mounted elsewhere), it is marked `orphaned` and the GC daemon retries with exponential backoff.

### 16.3.3 Garbage Collection Daemon

The `ocifbsd-gcd` daemon runs on every node:

```

│  ┌─────────────────────────────────────┐ │
```

## 16.4 Container Garbage Collection

### 16.4.1 Orphaned Jail Detection

Every jail created by `ocifbsd` has a `ocifbsd.owner` jail parameter:

```bash
$ jls -j web-1-main -v | grep ocifbsd.owner
  ocifbsd.owner: pod/web-1
  ocifbsd.created: 2026-04-29T14:32:01Z
  ocifbsd.stack: web-app
```

**Orphan detection logic:**
1. `ocifbsd-gcd` lists all jails with `ocifbsd.owner` set
2. For each jail, queries local state: does the owner pod still exist?
3. If owner pod does not exist → mark jail as `orphaned`
4. If owner pod exists but is in `Deleting` state → check deletion timestamp
5. If deletion timestamp + grace period < now → collect jail

### 16.4.2 Stopped Container Retention

Stopped containers (jails with `persist=0` that have exited) are retained for debugging:

```yaml
# /etc/ocifbsd/ocifbsd.conf
garbage_collection:
  containers:
    stopped_retention: 24h        # Keep stopped containers for 24 hours
    max_stopped_per_pod: 5        # Keep last 5 stopped containers per pod
    max_stopped_global: 100       # Global limit across all pods
```

When limits are exceeded, oldest stopped containers are deleted first.

### 16.4.3 Zombie Process Reaping

If a jail's init process exits but child processes remain (zombie or orphaned), `ocifbsd-gcd`:
1. Sends `SIGTERM` to all processes in the jail's PID namespace
2. Waits `termination_grace_period` (default: 30s)
3. Sends `SIGKILL` to any remaining processes
4. Destroys the jail

## 16.5 Image Garbage Collection

### 16.5.1 Unused Image Detection

Images are tracked with reference counts:

```
Image "nginx:1.25"
  ├── Layer sha256:abc... (refcount: 3)  ← used by nginx, app1, app2
  ├── Layer sha256:def... (refcount: 1)  ← used only by nginx
  └── Layer sha256:123... (refcount: 0)  ← unused, candidate for pruning
```

**Reference count sources:**
- Running pods using the image
- Stopped pods within retention window
- Explicit `ocifbsd image pin` by admin
- Base images referenced by child layers

### 16.5.2 Layer Deduplication and Cleanup

ZFS naturally deduplicates identical layers via snapshots and clones. The GC system:
1. Tracks which layers are referenced by which images
2. When an image is deleted, decrements layer refcounts
3. When a layer's refcount reaches 0, marks it for pruning
4. Pruning is deferred by `layer_grace_period` (default: 72h) to allow rollback

### 16.5.3 Image Pruning Policies

```yaml
garbage_collection:
  images:
    prune_interval: 1h
    unused_retention: 72h
    max_disk_usage_percent: 80    # Start aggressive pruning at 80% disk
    max_disk_usage_critical: 90   # Emergency pruning at 90%
    preserve_tags:
      - "latest"
      - "stable"
      - "production"
    preserve_recent: 10           # Always keep 10 most recently pulled images
```

**Emergency pruning:** When disk usage exceeds `max_disk_usage_critical`, GC:
1. Deletes all unreferenced layers immediately (no grace period)
2. Deletes stopped containers beyond minimum retention
3. Generates critical alert

## 16.6 Volume Garbage Collection

### 16.6.1 Orphaned Volume Detection

Volumes have `ocifbsd.owner` ZFS properties:

```bash
$ zfs get ocifbsd.owner zroot/ocifbsd/volumes/web-1-data
NAME                                    PROPERTY       VALUE          SOURCE
zroot/ocifbsd/volumes/web-1-data        ocifbsd.owner  volume/web-1   local
```

A volume is orphaned if:
- Its owner pod does not exist, OR
- Its owner pod exists but does not reference this volume, OR
- The volume is not mounted by any running jail and has no `ocifbsd.preserve` flag

### 16.6.2 ZFS Dataset Cleanup

Before destroying a volume dataset, GC:
1. Creates a final snapshot: `zroot/ocifbsd/volumes/web-1-data@gc-20260429-143201`
2. Retains snapshot for `snapshot_retention` (default: 7 days)
3. Destroys the dataset
4. If dataset has clones (derived datasets), promotes the clone or aborts deletion

### 16.6.3 Snapshot Retention Policies

```yaml
garbage_collection:
  volumes:
    snapshot_retention: 7d
    max_snapshots_per_volume: 10
    orphan_grace_period: 5m
    preserve_unmounted: false     # Delete volumes not mounted by any pod
```

## 16.7 Network Garbage Collection

### 16.7.1 Orphaned Bridge and epair Cleanup

Network interfaces created for pods are tagged:

```bash
$ ifconfig epair1a | grep ocifbsd
	ocifbsd.owner: pod/web-1
	ocifbsd.created: 2026-04-29T14:32:01Z
```

**GC process for network interfaces:**
1. List all `epair` interfaces with `ocifbsd.owner`
2. Check if owner pod exists
3. If orphaned, destroy `epair` pair and remove from bridge
4. If bridge has no remaining members, destroy bridge (unless marked persistent)

### 16.7.2 VXLAN Interface Cleanup

VXLAN interfaces are cluster-scoped. GC:
1. Only removes VXLAN interfaces when the namespace is deleted AND no pods in that namespace exist on any node
2. Coordinates with managers via gossip to confirm cross-node emptiness

### 16.7.3 Firewall Rule Cleanup

pf rules created for port forwarding are tagged with anchors:

```
pf anchor "ocifbsd/pod/web-1" {
  rdr pass on egress proto tcp from any to any port 8080 -> 10.0.1.5 port 80
}
```

When a pod is garbage collected, its pf anchor is removed automatically.

## 16.8 Cluster-Level Garbage Collection

### 16.8.1 Orphaned Node Resources

When a node is marked dead (missed heartbeats), the manager:
1. Checks if node will recover (maintenance mode? network partition?)
2. If node is truly dead, initiates **distributed orphan collection**:
   - Other nodes take over the dead node's pods (if replicas exist)
   - Pods that cannot be rescheduled are marked `orphaned`
   - When the dead node rejoins, it runs local GC to clean up stale jails

### 16.8.2 Distributed GC Coordination

Managers coordinate GC across the cluster:

```
Manager 1: "Node worker-3 missed 5 heartbeats. Initiating orphan scan."
Manager 2: "Ack. I will check if worker-3's pods have replicas elsewhere."
Manager 3: "Pod web-1 has replica on worker-2. Safe to mark orphan."
Manager 1: "Pod db-1 has no replicas. Initiating failover, not orphaning."
```

### 16.8.3 Cross-Node Orphan Detection

Some resources span nodes:
- **Shared volumes:** ZFS datasets replicated to multiple nodes
- **Load balancer backends:** Service endpoints pointing to pods on multiple nodes
- **VXLAN routes:** Routing entries for pods across the overlay

Cross-node GC uses the gossip protocol to:
1. Confirm resource is not referenced on any other node
2. Obtain distributed lock before deletion
3. Delete and propagate deletion event

## 16.9 Common Kubernetes Problems and Our Mitigations

### 16.9.1 ImagePullBackOff Loops

**Kubernetes problem:** A pod with a bad image spec enters `ImagePullBackOff`, retrying forever with exponential backoff. The pod object accumulates, cluttering the namespace.

**Our mitigation:**
- After 3 failed pulls, pod enters `Failed` state (not `ImagePullBackOff`)
- Failed pods are automatically deleted after `failed_pod_ttl` (default: 1h)
- Admin can inspect logs via `ocifbsd pod logs --previous` before deletion
- Event is generated: `Pod web-1 failed image pull 3 times; scheduled for deletion in 1h`

### 16.9.2 CrashLoopBackOff Accumulation

**Kubernetes problem:** A pod that crashes on startup enters `CrashLoopBackOff`, creating hundreds of restart attempts and log spam.

**Our mitigation:**
- After 5 crashes within 10 minutes, pod enters `Failed` state
- No automatic restart; admin must manually restart after fixing the issue
- `ocifbsd pod inspect web-1` shows crash history and last exit code
- Optional: `auto_restart: true` in pod spec for known-flaky workloads

### 16.9.3 Failed Job Pod Accumulation

**Kubernetes problem:** Completed or failed job pods are never cleaned up unless `ttlSecondsAfterFinished` is set (which many users forget).

**Our mitigation:**
- All batch jobs have a mandatory `ttl` field (default: 24h, minimum: 1h)
- `ocifbsd job create` rejects specs without TTL
- GC automatically deletes completed/failed job pods after TTL
- `ocifbsd job history` shows past jobs without keeping pods around

### 16.9.4 ConfigMap/Secret Leftovers

**Kubernetes problem:** ConfigMaps and Secrets are not deleted when the pod that uses them is deleted. They accumulate indefinitely.

**Our mitigation:**
- ConfigMaps and Secrets are inline in the pod spec (not separate objects)
- When pod is deleted, its ConfigMaps/Secrets are automatically deleted
- For shared ConfigMaps, explicit `shared: true` flag required; shared resources are reference-counted

### 16.9.5 PVC Orphans After Namespace Deletion

**Kubernetes problem:** Deleting a namespace with `kubectl delete namespace` hangs forever if PVCs have the `kubernetes.io/pvc-protection` finalizer. Admins resort to `--force --grace-period=0`, leaving PVCs orphaned.

**Our mitigation:**
- No finalizer-based deletion blocking. Cascade delete is immediate.
- If volume is in use, deletion fails with clear error: `Volume web-1-data is mounted by pod web-1; unmount before deleting`
- Admin can force with `--cascade=orphan` to delete namespace but keep volumes
- Orphaned volumes are detected and collected by GC within grace period

### 16.9.6 Stuck Terminating Pods

**Kubernetes problem:** A pod in `Terminating` state never finishes because a finalizer is stuck, a volume won't unmount, or a process ignores SIGTERM.

**Our mitigation:**
- `ocifbsd pod delete` has `--force` flag that bypasses graceful shutdown
- Force delete sends SIGKILL immediately, removes jail, cleans up resources
- Maximum graceful shutdown time: `termination_grace_period` (default: 30s, configurable per pod)
- After grace period, automatic SIGKILL + cleanup
- Event generated: `Pod web-1 force-killed after 30s grace period exceeded`

## 16.10 CLI Commands

```bash
# Trigger manual garbage collection
ocifbsd gc run

# List orphaned resources (dry-run)
ocifbsd gc orphans --dry-run

# List orphaned resources by type
ocifbsd gc orphans --type=jail
ocifbsd gc orphans --type=volume
ocifbsd gc orphans --type=image
ocifbsd gc orphans --type=network

# Clean up specific resource type
ocifbsd gc images --unused --older-than 72h
ocifbsd gc volumes --orphaned --grace-period 0
ocifbsd gc containers --stopped --older-than 24h

# Show GC statistics
ocifbsd gc stats

# Show GC events
ocifbsd gc events --since 24h

# Pin an image (prevent GC)
ocifbsd image pin nginx:1.25
ocifbsd image unpin nginx:1.25

# Configure GC policies
ocifbsd gc config set images.unused_retention 48h
ocifbsd gc config set containers.stopped_retention 12h
```

## 16.13 Future Enhancements

1. **Predictive GC:** Use ML to predict which images will be needed and pre-fetch them while pruning others
2. **Cross-cluster GC federation:** Federated clusters share GC state to prevent duplicate image storage
3. **Storage tiering:** Automatically move old snapshots to colder storage (tape, S3) before deletion
4. **GC simulation mode:** `ocifbsd gc simulate --dry-run=7d` shows what would be deleted after 7 days of normal operation
5. **Resource reclamation rewards:** Nodes that aggressively GC get priority for new pod scheduling (disk space is a scheduling resource)
