**Repository:** https://github.com/cloudbsdorg/freebsd-src-oci
**Branch:** `oci-plan`

## 14.1 Executive Summary

This document defines the observability and logging architecture for the FreeBSD native container orchestration system. While metrics tell you *what* is happening, logs tell you *why*. A production container platform without comprehensive logging is flying blind.

**Key Principles:**
- **Structured logs by default** — every log line is JSON, queryable, and machine-readable
- **Centralized collection** — all jail, host, and application logs flow to a single aggregation point
- **FreeBSD-native integration** — works with `syslogd`, `newsyslog`, and existing logging infrastructure
- **No log loss** — durable buffering ensures logs survive crashes and restarts
- **Sensible retention** — hot logs on ZFS SSD, warm logs on spinning disk, cold logs archived
- **Alerts, not noise** — actionable alerts with context, not pager storms

**What This Document Covers:**
| Area | Problem | Our Approach |
|------|---------|------------|
| Jail logs | Jails have isolated syslog; hard to aggregate | `ocifbsd-logd` collects from all jails via Unix socket |
| Container stdout | Docker captures stdout/stderr; jails don't | `ocifbsd` captures init process output automatically |
| Structured logging | FreeBSD syslog is unstructured | JSON envelope around every log line |
| Log retention | `newsyslog` is per-file, not per-service | ZFS dataset policies with automatic cleanup |
| Alerting | No built-in alerting in FreeBSD base | Rule engine with webhook/email/PagerDuty |
| SIEM integration | Manual log forwarding setup | Built-in fluentd/fluent-bit output |

## 14.2 Why Observability Matters

| Without Observability | With Observability |
|----------------------|-------------------|
| "The web service is slow" | "Pod web-3 on worker-2 has p95 latency of 2.3s due to CPU throttling at 14:32 UTC" |
| "Something crashed" | "Container nginx-7a3f exited with code 137 (OOM) at 09:15 UTC; memory limit was 128MB" |
| "The cluster is broken" | "Manager-1 Raft leader election failed; network partition between racks A and B detected" |
| "Why did it fail?" | "Deployment failed because image `app:v2.1` has critical CVE-2026-1234; blocked by policy" |

**Three Pillars of Observability:**
1. **Metrics** — quantitative data over time (covered in 8.0)
2. **Logs** — discrete events with context (this document)
3. **Traces** — request flow across services (future enhancement)

## 14.3 Logging Architecture

### 14.3.1 Log Pipeline Overview

```
┌─────────────────────────────────────────────────────────────────┐
│                        Log Pipeline                              │
│                                                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
│  │  Source  │→ │  Collect │→ │  Process │→ │  Store   │        │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘        │
│       │             │             │             │               │
│       ▼             ▼             ▼             ▼               │
│  Jail syslog    ocifbsd-     Enrich with   ZFS dataset       │
│  Host syslog    logd          metadata      /var/log/ocifbsd   │
│  App stdout     (Unix        (pod, node,   with snapshots     │
│  App stderr     socket)       timestamp)   and compression    │
│  Audit logs                   Filter and                      │
│  Event stream                 deduplicate                     │
│                                                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                     │
│  │  Query   │  │  Alert   │  │ Forward  │                     │
│  │  (CLI)   │  │  (rules) │  │ (SIEM)   │                     │
│  └──────────┘  └──────────┘  └──────────┘                     │
└─────────────────────────────────────────────────────────────────┘
```

### 14.3.2 Log Sources

| Source | Description | Collection Method |
|--------|-------------|-------------------|
| **Jail syslog** | `/var/log/messages` inside each jail | `ocifbsd-logd` reads via mounted log socket |
| **Host syslog** | FreeBSD host system logs | Direct read from `/var/log` |
| **Container stdout** | Output from container init process | `ocifbsd` captures via pipe |
| **Container stderr** | Error output from container init process | `ocifbsd` captures via pipe |
| **Audit logs** | Security and RBAC audit events | Written directly by `ocifbsdd` |
| **Event stream** | Cluster events (pod start, stop, migrate) | Generated by orchestrator |
| **Health checks** | Health check results and failures | Generated by `healthd` |
| **Metrics** | Metric snapshots at log time | Attached as log metadata |

### 14.3.3 Log Aggregation Daemon

`ocifbsd-logd` is the central log collection daemon. It runs on every node:

```
ocifbsd-logd
  ├── Unix socket: /var/run/ocifbsd/log.sock
  │     └── Jails and containers write JSON logs here
  ├── File watcher: /var/log/ocifbsd/
  │     └── Host system logs are read and enriched
  ├── Buffer: In-memory ring buffer (survives restarts via mmap)
  │     └── Durable buffering prevents log loss
  └── Output plugins:
        ├── ZFS dataset (local storage)
        ├── syslogd (traditional forwarding)
        ├── fluent-bit (modern forwarding)
        └── webhook (event-driven)
```

**Daemon properties:**
- Runs as `ocifbsd` user (not root)
- Uses `kqueue` for efficient file watching
- Buffers up to 100MB in memory, flushes to ZFS every 5 seconds
- Survives crashes: mmap buffer is recovered on restart

## 14.4 Structured Logging

### 14.4.1 JSON Log Format

Every log line is a JSON object:

```json
{
  "timestamp": "2026-04-29T14:32:01.123Z",
  "severity": "ERROR",
  "source": "jail",
  "node": "worker-2",
  "namespace": "production",
  "stack": "web",
  "pod": "nginx-7a3f",
  "container": "nginx",
  "message": "worker process 1234 exited on signal 9",
  "attributes": {
    "pid": 1234,
    "signal": 9,
    "image": "nginx:1.25"
  },
  "trace_id": "abc123def456",
  "span_id": "span789"
}
```

### 14.4.2 Common Fields

| Field | Type | Description | Required |
|-------|------|-------------|----------|
| `timestamp` | ISO 8601 | Event time in UTC | Yes |
| `severity` | string | `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` | Yes |
| `source` | string | `host`, `jail`, `container`, `audit`, `event` | Yes |
| `node` | string | Hostname of the node | Yes |
| `namespace` | string | Namespace name (if applicable) | No |
| `stack` | string | Stack name (if applicable) | No |
| `pod` | string | Pod name (if applicable) | No |
| `container` | string | Container name (if applicable) | No |
| `message` | string | Human-readable log message | Yes |
| `attributes` | object | Key-value pairs for structured data | No |
| `trace_id` | string | Distributed trace ID (if applicable) | No |
| `span_id` | string | Span ID within trace (if applicable) | No |

### 14.4.3 Severity Levels

| Level | Numeric | Use Case | Example |
|-------|---------|----------|---------|
| `DEBUG` | 10 | Development troubleshooting | "Opened connection to database pool" |
| `INFO` | 20 | Normal operational events | "Pod nginx-7a3f started successfully" |
| `WARN` | 30 | Anomalies that don't affect service | "High memory usage: 85% of limit" |
| `ERROR` | 40 | Failures that affect functionality | "Container exited with code 1" |
| `FATAL` | 50 | System-wide failures | "ZFS pool corruption detected" |

**Default log level:** `INFO` (configurable per-namespace and per-service)

## 14.5 Log Collection from Jails

### 14.5.1 Jail Log Forwarding

Jails write to `/var/log/messages` inside their rootfs. `ocifbsd-logd` mounts a Unix socket into each jail:

```
Jail filesystem:
  /dev/log → /var/run/ocifbsd/log.sock (bind mount)

Jail syslogd writes to /dev/log → captured by ocifbsd-logd
```

**Configuration:**
```yaml
# /etc/ocifbsd/ocifbsd.conf
logging:
  jail_forwarding:
    enabled: true
    socket_path: /var/run/ocifbsd/log.sock
    # Mount the socket into every jail automatically
    auto_mount: true
```

### 14.5.2 Container stdout/stderr Capture

When `ocifbsd` starts a container, it captures stdout and stderr:

```bash
$ ocifbsd run --name myapp --log-driver json myimage
```

The `json` log driver wraps each line:
```json
{
  "timestamp": "2026-04-29T14:32:01.123Z",
  "severity": "INFO",
  "source": "container",
  "stream": "stdout",
  "node": "worker-1",
  "namespace": "default",
  "pod": "myapp",
  "container": "myapp",
  "message": "Server listening on port 8080"
}
```

**Log drivers:**
| Driver | Description | Use Case |
|--------|-------------|----------|
| `json` | Structured JSON logs (default) | Production |
| `syslog` | Forward to syslogd | Legacy integration |
| `none` | Discard logs | Ephemeral/debug |
| `fluentd` | Forward to fluentd/fluent-bit | SIEM integration |

### 14.5.3 Application Log Injection

Applications can inject structured logs directly:

```bash
# Inside a container, write to the log socket
echo '{"severity":"INFO","message":"Custom event"}' > /dev/log
```

Or use the `ocifbsd-log` helper:
```bash
$ ocifbsd-log --severity=WARN --attribute=key=value "Something happened"
```

## 14.6 Log Storage and Retention

### 14.6.1 ZFS-Based Log Storage

Logs are stored in a dedicated ZFS dataset:

```
zroot/ocifbsd/logs/
  ├── current/          # Active logs (last 24h)
  │     └── 2026-04-29/
  │           ├── worker-1.jsonl
  │           ├── worker-2.jsonl
  │           └── events.jsonl
  ├── archive/          # Compressed historical logs
  │     └── 2026-03/
  │           ├── worker-1.jsonl.zst
  │           └── worker-2.jsonl.zst
  └── index/            # SQLite index for fast queries
        └── logs.db
```

**ZFS properties:**
```bash
# Create log dataset
zfs create -o compression=zstd -o atime=off zroot/ocifbsd/logs
zfs set quota=100G zroot/ocifbsd/logs
```

### 14.6.2 Retention Policies

```yaml
# /etc/ocifbsd/ocifbsd.conf
logging:
  retention:
    hot:      # Fast SSD access
      duration: 7d
      compression: none
    warm:     # Spinning disk or slower SSD
      duration: 30d
      compression: zstd
    cold:     # Archive
      duration: 365d
      compression: zstd
      # Auto-delete after cold period
      delete_after: 730d
```

### 14.6.3 Log Rotation

`ocifbsd-logd` handles rotation internally:

```
Rotation triggers:
  - Size: 100MB per file
  - Time: Daily at 00:00 UTC
  - Manual: ocifbsd log rotate

Rotation action:
  1. Close current file
  2. Rename to YYYY-MM-DD-HHMMSS.jsonl
  3. Compress if warm/cold tier
  4. Open new file
  5. Update SQLite index
```

### 14.6.4 Compression and Archival

| Tier | Compression | Trigger | Access Time |
|------|-------------|---------|-------------|
| Hot | None | Active | < 1ms |
| Warm | zstd | After 7 days | < 10ms |
| Cold | zstd + dedup | After 30 days | < 100ms |

**ZFS send for offsite archival:**
```bash
# Weekly snapshot and send to backup server
$ zfs snapshot zroot/ocifbsd/logs@weekly-$(date +%Y%m%d)
$ zfs send zroot/ocifbsd/logs@weekly-20260429 | ssh backup zfs recv tank/archives/ocifbsd-logs
```

## 14.7 Log Forwarding and Integration

### 14.7.1 Syslog Integration

Forward logs to the host `syslogd` for traditional processing:

```yaml
logging:
  forwarders:
    syslog:
      enabled: true
      facility: local0
      severity_map:
        DEBUG: debug
        INFO: info
        WARN: warning
        ERROR: err
        FATAL: emerg
```

### 14.7.2 Fluentd/Fluent Bit Forwarding

Modern log forwarding via Fluent Bit protocol:

```yaml
logging:
  forwarders:
    fluentbit:
      enabled: true
      host: fluentd.internal
      port: 24224
      tls: true
      # Tag format: ocifbsd.<node>.<namespace>.<pod>
      tag_prefix: ocifbsd
```

### 14.7.3 SIEM Integration

Direct integration with common SIEM platforms:

| SIEM | Protocol | Configuration |
|------|----------|---------------|
| Splunk | HEC (HTTP Event Collector) | `host`, `token`, `index` |
| ELK | Elasticsearch bulk API | `hosts`, `index_pattern` |
| Graylog | GELF (UDP/TCP) | `host`, `port` |
| Datadog | Datadog Agent | `api_key`, `site` |

```yaml
logging:
  forwarders:
    splunk:
      enabled: true
      host: splunk.internal:8088
      token: ${SPLUNK_HEC_TOKEN}
      index: ocifbsd
      sourcetype: _json
```

### 14.7.4 Cloud Log Services

```yaml
logging:
  forwarders:
    aws_cloudwatch:
      enabled: true
      region: us-east-1
      log_group: /ocifbsd/cluster
      # Uses IAM role or credentials file
```

## 14.8 Alerting

### 14.8.1 Alert Rules

Alert rules are defined in YAML:

```yaml
# /etc/ocifbsd/alerts.yml
alerts:
  - name: high_cpu_usage
    condition: |
      metric: cpu_usage_percent
      threshold: > 90
      duration: 5m
      for: pod in namespace production
    severity: warning
    summary: "High CPU usage on {{ pod.name }}"
    description: "CPU usage has been above 90% for 5 minutes"

  - name: container_crash_loop
    condition: |
      log: severity = ERROR
      pattern: "exited with code"
      count: > 3
      window: 10m
      for: container
    severity: critical
    summary: "Container {{ container.name }} is crash-looping"

  - name: disk_space_low
    condition: |
      metric: zfs_dataset_available_bytes
      threshold: < 10GB
      for: dataset zroot/ocifbsd/logs
    severity: warning
    summary: "Log disk space low on {{ node.name }}"
```

### 14.8.2 Notification Channels

| Channel | Configuration | Use Case |
|---------|--------------|----------|
| Email | SMTP server, recipients | Non-urgent alerts |
| Slack | Webhook URL | Team notifications |
| PagerDuty | Integration key | Critical alerts |
| Webhook | URL, headers, payload | Custom integrations |
| SMS | Twilio API | Emergency alerts |

```yaml
notifications:
  - name: ops_team
    channel: slack
    webhook: https://hooks.slack.com/services/xxx
    # Only send WARNING and above
    min_severity: warning

  - name: on_call
    channel: pagerduty
    integration_key: ${PAGERDUTY_KEY}
    min_severity: critical
```

### 14.8.3 Alert Manager

`ocifbsd-alertd` evaluates rules and sends notifications:

```
Alert lifecycle:
  1. Rule evaluation (every 30s)
  2. Condition met → Create alert (PENDING)
  3. Duration satisfied → Fire alert (FIRING)
  4. Send notification
  5. Condition clears → Resolve alert (RESOLVED)
  6. Send resolution notification
```

**Alert grouping:**
- Group by: `namespace`, `stack`, `alertname`
- Throttle: Max 1 notification per 5 minutes per group
- Silence: Manual suppression with expiration

## 14.9 Event Stream

### 14.9.1 Event Types

| Event | Description | Severity |
|-------|-------------|----------|
| `pod.created` | Pod was created | INFO |
| `pod.started` | Pod started successfully | INFO |
| `pod.stopped` | Pod stopped | INFO |
| `pod.crashed` | Pod exited unexpectedly | ERROR |
| `pod.migrated` | Pod migrated to another node | INFO |
| `node.joined` | Node joined cluster | INFO |
| `node.left` | Node left cluster | WARN |
| `node.failed` | Node marked unhealthy | ERROR |
| `image.pulled` | Image pulled from registry | INFO |
| `deployment.completed` | Rolling update finished | INFO |
| `deployment.failed` | Rolling update failed | ERROR |
| `security.violation` | Policy violation detected | ERROR |
| `auth.failure` | Authentication failure | WARN |

### 14.9.2 Event Subscription

Subscribe to events via CLI or API:

```bash
# Watch all events in real-time
$ ocifbsd events --follow

# Filter by type
$ ocifbsd events --type=pod.crashed --namespace=production

# Filter by severity
$ ocifbsd events --severity=ERROR --since=1h
```

### 14.9.3 Webhook Delivery

Register webhooks for event-driven integrations:

```yaml
# /etc/ocifbsd/webhooks.yml
webhooks:
  - name: ci_pipeline
    url: https://ci.example.com/webhook/ocifbsd
    events:
      - deployment.completed
      - deployment.failed
    headers:
      Authorization: Bearer ${CI_TOKEN}

  - name: monitoring
    url: https://monitoring.internal/events
    events:
      - pod.crashed
      - node.failed
    # Retry failed deliveries
    retry: 3
    timeout: 10s
```

## 14.10 CLI Commands

| Command | Description |
|---------|-------------|
| `ocifbsd logs` | Show logs for a pod, stack, or namespace |
| `ocifbsd logs --follow` | Follow logs in real-time |
| `ocifbsd logs --since 1h` | Logs from last hour |
| `ocifbsd logs --severity ERROR` | Only error logs |
| `ocifbsd logs --tail 100` | Last 100 lines |
| `ocifbsd events` | Show cluster events |
| `ocifbsd events --follow` | Watch events in real-time |
| `ocifbsd alert ls` | List active alerts |
| `ocifbsd alert ack <id>` | Acknowledge an alert |
| `ocifbsd alert silence <name>` | Silence an alert rule |
| `ocifbsd log query '<expr>'` | Query logs with expression |

**Examples:**
```bash
# Follow logs for a specific pod
$ ocifbsd logs --pod nginx-7a3f --follow

# Search for errors across all pods in a namespace
$ ocifbsd logs --namespace production --severity ERROR --since 1h

# Query with structured search
$ ocifbsd log query 'severity=ERROR AND pod=web-* AND message~"connection refused"'

# Show recent events
$ ocifbsd events --since 30m

# List and acknowledge alerts
$ ocifbsd alert ls
ALERT ID   NAME              SEVERITY   SINCE   POD
alert-123  high_cpu_usage    warning    5m      web-3
$ ocifbsd alert ack alert-123
```

## 14.11 Configuration

```yaml
# /etc/ocifbsd/ocifbsd.conf
logging:
  # Global log level
  level: INFO

  # Log aggregation daemon
  logd:
    enabled: true
    socket_path: /var/run/ocifbsd/log.sock
    buffer_size: 100MB
    flush_interval: 5s

  # Storage
  storage:
    dataset: zroot/ocifbsd/logs
    quota: 100G
    hot_duration: 7d
    warm_duration: 30d
    cold_duration: 365d
    delete_after: 730d

  # Rotation
  rotation:
    max_size: 100MB
    max_age: 1d
    compress: true

  # Forwarders
  forwarders:
    syslog:
      enabled: false
    fluentbit:
      enabled: false
    splunk:
      enabled: false

  # Alerting
  alerting:
    enabled: true
    evaluation_interval: 30s
    rules_file: /etc/ocifbsd/alerts.yml

  # Events
  events:
    retention: 30d
    webhooks:
      enabled: true
      config: /etc/ocifbsd/webhooks.yml
```
