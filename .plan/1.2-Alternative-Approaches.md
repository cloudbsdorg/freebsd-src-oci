## 5. Why Current Implementations Fall Short

This section examines existing container tooling on FreeBSD and explains why each approach fails to deliver a native, performant, and maintainable solution. These are not "alternatives we considered and rejected" — these are the tools that exist today, and they are fundamentally inadequate for production FreeBSD container workloads.

---

### 5.1 Port podman to FreeBSD

**What it is:** The `podman-suite` port attempts to run Podman (a Linux-native container engine) on FreeBSD through a growing pile of compatibility patches.

**Problems, Inadequacies, and Pitfalls:**
- **Linux compatibility layer dependency hell.** Podman assumes cgroup v2, seccomp, overlayfs, and a dozen other Linux-specific interfaces. Every one of these must be emulated, shimmed, or patched on FreeBSD. The result is a fragile tower of abstractions that breaks on every upstream Podman release.
- **Perpetual maintenance treadmill.** Each new Podman version requires re-porting patches, re-testing compatibility shims, and chasing upstream API changes. This is not sustainable for a production platform.
- **Performance overhead from emulation.** Every container operation goes through translation layers. `jexec` becomes a compatibility shim instead of a first-class primitive. ZFS datasets are treated as foreign objects rather than native storage.
- **Ignores FreeBSD's actual strengths.** Podman on FreeBSD cannot leverage VNET for proper network isolation, cannot use RCTL for fine-grained resource control, and cannot use ZFS snapshots for efficient image layers. It treats FreeBSD as a broken Linux instead of a capable host.

**The honest assessment:** The `podman-suite` port is a heroic effort by dedicated maintainers, but it is fundamentally the wrong approach. It asks FreeBSD to be Linux rather than asking container tooling to be native. Production workloads deserve better than compatibility layers.

### 5.2 Use Linux KVM/Bhyve for Containers

**What it is:** Running full Linux VMs under bhyve/KVM and treating each VM as a "container host."

**Problems, Inadequacies, and Pitfalls:**
- **Full VM overhead per container.** A container is supposed to share the host kernel. Running a full Linux kernel inside bhyve for every workload defeats the entire purpose. You get none of the density benefits that make containers attractive.
- **Does not solve native FreeBSD container needs.** If your application needs to run on FreeBSD, a Linux VM inside bhyve is useless. This approach only helps you run Linux workloads on FreeBSD hardware — it does nothing for FreeBSD-native containers.
- **Resource waste at scale.** Memory deduplication helps, but you are still running N kernels, N init systems, and N copies of userspace for N containers. On a 128GB host, you might fit 200 native jails or 20 bhyve VMs. The math is not favorable.
- **Breaks the OCI runtime contract.** The OCI specification explicitly expects containers to share the host kernel. A VM-based "container" is not a container — it is a VM with extra steps. Tooling, monitoring, and orchestration all break down when your "containers" are actually VMs.

**The honest assessment:** Bhyve is excellent for what it is — a Type-2 hypervisor for full VMs. Using it for containers is like using a semi-truck to deliver a letter. It works, but it is the wrong tool, and it scales poorly.

### 5.3 Extend runc for FreeBSD

**What it is:** Attempting to port `runc` (the reference OCI runtime implementation) to FreeBSD by adding FreeBSD-specific code paths.

**Problems, Inadequacies, and Pitfalls:**
- **Deeply tied to Linux kernel interfaces.** `runc` is built around cgroups, Linux namespaces, seccomp, and procfs. These are not "features" — they are the foundation of the codebase. Porting `runc` to FreeBSD requires reimplementing its core assumptions from scratch.
- **Massive #ifdef proliferation.** Every file in `runc` that touches cgroups, namespaces, or seccomp would need parallel FreeBSD implementations. The codebase would become unreadable, unmaintainable, and impossible to test.
- **Fundamental model mismatch.** Linux namespaces are a fine-grained, composable system. FreeBSD jails are a coarse-grained, integrated system. `runc` expects to assemble containers from namespace primitives. Jails are already assembled. Forcing `runc` to understand jails is like teaching a fish to ride a bicycle.
- **Designing for Linux instead of FreeBSD.** Even a successful `runc` port would produce a runtime that thinks like Linux. It would not leverage ZFS for image layers, would not use VNET for networking, and would not integrate with FreeBSD's resource control framework. It would be a second-class citizen on its own operating system.

**The honest assessment:** `runc` is a reference implementation for Linux. It serves that role well. Attempting to make it the reference implementation for FreeBSD is a category error. FreeBSD deserves its own reference runtime designed around jails, ZFS, and VNET — not a Linux runtime wearing a FreeBSD costume.

## 5.4 The Common Theme

All three approaches share the same fundamental flaw: **they treat FreeBSD as a defective Linux.** They start from the assumption that the Linux way is the right way, and FreeBSD must be adapted to fit. This is backwards.

FreeBSD has:
- **Jails** — a mature, secure container primitive that predates Docker by over a decade
- **ZFS** — a filesystem with built-in snapshots, compression, and replication that makes overlayfs look like a toy
- **VNET** — network stack virtualization that is more powerful and cleaner than Linux network namespaces
- **RCTL** — resource control that is simpler and more capable than cgroups v1/v2
- **MAC** — mandatory access control that integrates cleanly with the system

The right approach is not to port Linux container tooling to FreeBSD. The right approach is to build container tooling that treats FreeBSD's native capabilities as first-class primitives. That is what this project does.
